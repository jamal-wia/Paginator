# Reactive Sources

[← Back to README](../README.md)

This page covers bridging the paginator to a **reactive source of truth** —
typically a local database (Room, SQLDelight, Realm), but also a WebSocket
feed, Server-Sent Events stream, in-app event bus, or any other source whose
contents change independently of the paginator's `load` lambda. The goal is
to keep the visible pages in sync with the source without re-fetching pages
on every mutation.

## Choosing a Bridge

The library has two bridges from a reactive source to a `MutablePaginator`. They are mutually
exclusive on one paginator — starting one while the other is active throws `IllegalStateException`.

| Your source can…                                                        | Use                                                          |
|-------------------------------------------------------------------------|--------------------------------------------------------------|
| observe **one page at a time** (`LIMIT` / `OFFSET` query re-emitting on table change — Room, SQLDelight) | [`observePages()`](#per-page-live-queries-observepages)      |
| emit **change events** (inserted / updated / removed) or whole snapshots | [`observe()` + `PaginatorReactiveCache`](#api-at-a-glance)   |

`observePages()` is offset-only (`paginator-offset`); `observe()` exists for both strategies.

## Per-Page Live Queries: `observePages()`

When the database can already observe a page — Room adds triggers to the table and re-emits a
query's result on every change — there is nothing to translate into events. `observePages()`
backs every cached page with its own live query instead of a one-shot `load`:

```kotlin
@Dao
interface UserDao {
    @Query("SELECT * FROM users ORDER BY name LIMIT :limit OFFSET :offset")
    fun observeUsers(limit: Int, offset: Int): Flow<List<User>>
}

// `load` is not called while the pages are observed.
val paginator = MutablePaginator<User>(load = { LoadResult(emptyList()) })

val job: Job = paginator.observePages(scope = viewModelScope) { page ->
    dao.observeUsers(limit = core.capacity, offset = (page - 1) * core.capacity)
}

// Navigate exactly as before — scroll, prefetch, jump, refresh.
paginator.goNextPage()

override fun onCleared() = job.cancel()
```

Only the pages in the cache are subscribed, so this works for tables far larger than the cache:
scrolling subscribes the newly loaded pages, eviction unsubscribes the ones that fell out.

With the [DSL builder](11.%20dsl-builder.md#livepages----live-database-pages-mutablepaginator-only)
the same setup needs no `load` and no separate call — the subscriptions live as long as the scope:

```kotlin
val paginator = mutablePaginator<User>(capacity = 20) {
    livePages(viewModelScope) { page ->
        dao.observeUsers(limit = core.capacity, offset = (page - 1) * core.capacity)
    }
}
```

### How a page lives

1. **Load = subscribe.** Loading page `N` by any navigation call subscribes to `source(N)` and uses
   its **first** emission as the load result (the usual Progress → Success pipeline). A flow that
   fails before emitting gives an Error page, like a throwing `load`. `refresh` (and the dirty-page
   refresh) re-subscribes.
2. **Emissions = updates.** Every later emission replaces the page's data in place. The page keeps
   its id and class, the data is trimmed to `capacity`, and the result is exactly what a fresh load
   would have produced — an emptied page is an empty Success page, and a page of the window that
   shrank (at an edge or inside) re-anchors the window like a CRUD removal does, so a non-filled
   page never stays buried inside it. Updates that are pending together are applied as one batch
   with one snapshot.
3. **Leaving the cache = unsubscribe.** A query lives as long as its page is cached: eviction
   strategies, `restart`, `release`, `removeState` and transaction rollback end the affected
   subscriptions; `core.resize` restarts them with the new capacity. This holds for silent calls
   too (`silently = true`, `silentlyResult = true`) — the subscriptions are reconciled after every
   finished operation, not only when a snapshot is published.
4. **Cancelled loads.** If a navigation that loads a page is cancelled, the page rolls back to its
   previous state and its query is subscribed again — the page stays live.
5. **Pages that entered the cache without a load** — restored by `restoreState`, created by CRUD
   overflow, or loaded before `observePages()` was called — are subscribed on the fly, so every
   cached Success page is live.
6. **Wholesale replacement = resubscribe.** `restoreState` / `restoreStateFromJson` (also with
   `silently = true`), a transaction rollback and a `removeState` that relabels the pages above it
   leave cached pages with data their queries never emitted — and Room will not emit again until the
   table changes. So every live page is
   re-queried right away, and its first emission puts the database's current content back.

#### Recreated paginator (process death)

A paginator restored from a saved state subscribes to **all** its restored pages at once, not
page by page as the user scrolls — whether `observePages()` is called before or after
`restoreStateFromJson(...)`:

```kotlin
val paginator = MutablePaginator<User>(load = { LoadResult(emptyList()) })
savedStateHandle.get<String>("users")?.let { paginator.restoreStateFromJson(it, User.serializer()) }

paginator.observePages(viewModelScope) { page ->
    dao.observeUsers(limit = core.capacity, offset = (page - 1) * core.capacity)
}
```

The restored data shows instantly (no loading state), then each page's first emission replaces it
with what the database holds now — rows changed while the process was dead are not lost. First
emissions that arrive together are applied as one batch (queries that answer later update the UI
again). Restoring N pages means N
queries at once; N is bounded by your cache strategy. Pages saved as Error / Progress are restored
dirty, so the next navigation that reaches them reloads them once more.

If a flow fails **after** its first emission, `onError(page, error)` is called and the page is
marked dirty: it keeps its last data, and the next navigation that reaches it reloads — and
re-subscribes — it. A flow that completes normally simply stops updating its page. One page's
failure never affects the other pages, and an `onError` that throws is logged, not propagated —
nothing from `observePages` escapes into your scope.

Cancelling the returned `Job` (or its scope) cancels every page subscription and restores the
paginator's original `load`. A load that was waiting for its page's first emission at that moment
falls back to the original `load` instead of producing an error page.

### Consistent updates across pages: `settle`

A table change makes the database re-run **every** query of that table, and each live page answers
— but at different moments. Without coordination the screen can show page 1 *after* a row moved
up while page 2 still shows it *before*: the row appears twice (a lazy list keyed by item id
crashes on duplicate keys) or, for an insert, disappears for a moment.

`settle` turns the updates into **rounds**:

```kotlin
paginator.observePages(viewModelScope, settle = 100.milliseconds) { page ->
    dao.observeUsers(limit = core.capacity, offset = (page - 1) * core.capacity)
}
```

- The first emission after a change opens a round. Its update is held until **every other live
  page has emitted too** — then the whole round is applied as one batch with one snapshot.
- If some page has nothing to emit (a source that skips unchanged results), the round is applied
  once `settle` has passed since it opened.
- Loads are not delayed: a page's first emission still completes its navigation immediately.

So a row moving across pages is never shown twice or missed, at the cost of latency: an update
waits for the slowest page query, at most `settle`. Choose a value a little above your page query
time. Room and SQLDelight re-emit every query on a table change, so rounds usually close long
before the timeout. `settle` is off by default (`Duration.ZERO`) and is also available on
`observePageResults` and in the DSL (`livePages(scope, settle = …)`).

### Metadata: `observePageResults()`

If each emission should also carry page metadata (a total count, a server cursor, …), return
`Flow<LoadResult<T>>` from `observePageResults()` — non-null metadata replaces the page's metadata:

```kotlin
paginator.observePageResults(viewModelScope) { page ->
    dao.observeUsers(core.capacity, (page - 1) * core.capacity)
        .combine(dao.observeUserCount()) { users, total -> LoadResult(users, TotalCount(total)) }
}
```

### Interaction with the rest of the library

- **Navigation lock & threads.** Every cache access of `observePages` — live writes and its own
  bookkeeping — holds the paginator's navigation lock, so it never interleaves with `jump` /
  `goNextPage` / `restart` and is safe on a multi-threaded dispatcher (`Dispatchers.Default` /
  `IO`). An update that lands while `refresh` is loading the same page wins over the refresh's
  older result (see [refresh](2.%20navigation.md#refresh)), and the page does not stay dirty.
- **CRUD.** The database is the source of truth: an element-level edit on a live page is overwritten
  by that page's next emission. Change the database, not the paginator.
- **`observe()`.** Mutually exclusive with `observePages()`, see [Choosing a Bridge](#choosing-a-bridge).
- **Eviction strategies.** A page's query ends when any strategy evicts the page. Database
  emissions and observePages' own bookkeeping are **not** a use of a page: they go through
  [`setStateUntracked` / `peekStateOf`](6.%20caching.md#untracked-access--setstateuntracked--peekstateof),
  so an LRU cache still evicts the least recently *visited* page and a TTL cache still expires a
  page by the time it was loaded, however often its rows change.
- **L2.** The deprecated [persistent cache](6.%20caching.md#persistent-cache-l2) is redundant here and
  not supported; a warning is logged when one is attached.
- **Neighbouring pages update independently** — unless you pass `settle`, see
  [Consistent updates across pages](#consistent-updates-across-pages-settle). Each page is its own
  query, and the database answers the queries one by one. By default, right after a change that
  shifts rows across page boundaries, adjacent pages update at different moments, and until the
  slower query answers the same row can appear on two adjacent pages (or briefly on none).

## API at a Glance

Two things to implement, one extension to call, one `Job` to cancel:

```kotlin
// 1) Implement the adapter — two methods.
class UserReactiveCache(dao: UserDao) : PaginatorReactiveCache<User, Long> {
    override fun identity(item: User): Long = item.id
    override fun changes(): Flow<ReactiveEvent<User, Long>> = dao.observeChanges()
}

// 2) Wire it to the paginator and keep the Job.
val job: Job = paginator.observe(
    scope = viewModelScope,
    source = UserReactiveCache(dao),
)

// 3) Cancel it when the consumer goes away.
override fun onCleared() {
    job.cancel()
}
```

Everything else on this page — events, positions, policies, adapter tiers —
fills in what `dao.observeChanges()` should actually emit and which
behavioural knobs you might want to turn.

## Data Flow

```
┌────────────┐    Flow<ReactiveEvent<T, ID>>    ┌─────────────┐    CRUD     ┌──────────┐
│  Source    │ ───────────────────────────────► │  observe()  │ ──────────► │  L1      │
│ (DAO, WS,  │                                  │  collector  │             │  cache   │ ──► UI
│  bus, …)   │                                  │             │             │          │
└────────────┘                                  └─────────────┘             └──────────┘
       ▲                                                                          │
       └────────── load(page)  (one-shot fetch, never invoked per-event) ─────────┘
```

The `load` lambda is still called for fresh pages (jump, paginate, refresh).
The reactive path is parallel — every event from `changes()` is translated to
a CRUD op on the L1 cache, *not* into a new `load`. The two paths converge in
the cache and the UI sees a single coherent state.

## The Antipattern: navigation from inside `load`

Do **not** call any navigation/refresh function from inside the `load`
lambda — `refresh`, `refreshAll`, `jump`, `jumpForward`, `jumpBack`,
`goNextPage`, `goPreviousPage`, `restart`, `saveState`, `restoreState`.

These all acquire `navigationMutex` at entry, and the outer call that
triggered your `load` already holds it. Since the mutex is non-reentrant,
the inner call will deadlock — your UI hangs with no error and no log.

CRUD operations (`setElement`, `removeElement`, `addAllElements` and the
extension helpers) do not take the mutex and are safe to call from inside
`load`.

For reactive sources, subscribe from *outside* `load` — see the next
section.

## The Solution: `observe()` + `PaginatorReactiveCache`

Subscribe to the reactive source from *outside* `load`, and let the
paginator translate each change to the matching CRUD operation:

```kotlin
val paginator = mutablePaginator<User> {
    capacity = 20
    load { page -> dao.getPage(page, capacity) }   // one-shot fetch
}

val subscription: Job = paginator.observe(
    scope = viewModelScope,
    source = UserReactiveCache(dao),               // implementations below
    initialSync = InitialSyncPolicy.RefreshAll,
    unknownItem = UnknownItemPolicy.Drop,
)
```

Cancel the returned `Job` when the consumer goes away (Activity destroy,
Composable disposal, ViewModel clear). The paginator does *not* own the
subscription's lifetime. See [Lifecycle & Cancellation](#lifecycle--cancellation).

> ⚠️ **One active subscription per paginator.** A second `observe()` call
> while a previous `Job` is still active throws `IllegalStateException`.
> Cancel the previous Job first. A completed/cancelled Job releases the slot
> automatically.

## Event Catalog

The adapter emits [
`ReactiveEvent<T, ID>`](../paginator-core/src/commonMain/kotlin/com/jamal_aliev/paginator/core/cache/reactive/ReactiveEvent.kt)
s
on its `changes()` flow. The paginator dispatches each event to the matching
CRUD operation:

| Event                      | What the paginator does                                                                           |
|----------------------------|---------------------------------------------------------------------------------------------------|
| `Updated(item)`            | Replaces the cached item whose `identity(cached) == identity(item)`.                              |
| `Removed(identity)`        | Removes the cached item with the matching identity (cascades from next page).                     |
| `Inserted(item, position)` | Inserts at the given [`InsertPosition`](#insert-positions); overflow cascades and may create a trailing page (see [`initPageState`](#initpagestate--overflow-page-creation)). |
| `Moved(item, position)`    | Transactional remove + insert at a new position. Doubles as `Updated` (item may have new fields). |
| `Invalidate`               | Runs `refreshAll()` — every cached page is re-fetched via `load`.                                 |
| `Batch(events)`            | Wraps applying the listed events in `transaction { … }` — all-or-nothing.                         |

Events are applied **in arrival order**. The paginator serialises application
internally, so adapters do not need to add their own synchronisation.

## Insert Positions

[
`InsertPosition<ID>`](../paginator-core/src/commonMain/kotlin/com/jamal_aliev/paginator/core/cache/reactive/InsertPosition.kt)
encodes where a new item lands. Pick the one that matches the source's
ordering:

| Position                 | When to use                                                                |
|--------------------------|----------------------------------------------------------------------------|
| `Head`                   | Newest-first feeds — every insert goes to position `(firstPage, 0)`.       |
| `Tail`                   | Oldest-first feeds — every insert goes to the end of the last cached page. |
| `At(page, index)`        | Absolute coordinate. Use sparingly; survives badly across page rebalance.  |
| `AfterIdentity(anchor)`  | Insert immediately after the item with `identity == anchor`.               |
| `BeforeIdentity(anchor)` | Insert immediately before the item with `identity == anchor`.              |

If the adapter cannot compute a meaningful position (e.g., a complex
`ORDER BY` it cannot mirror), emit `Invalidate` instead of guessing. The
paginator will run `refreshAll()` and the source-of-truth ordering wins.

## Policies

### `InitialSyncPolicy`

Controls what `observe()` does about the gap between the most recent page
load and the first observed event:

- **`RefreshAll` (default)** — issue `refreshAll()` immediately after
  subscribe. Costs one extra load per cached page, but eliminates the chance
  of missed updates that happened during the gap.
    - **No-op when the cache is empty at subscribe time** (you called
      `observe()` before any page had loaded). There is nothing to reconcile —
      the upcoming first `load()` will already see the latest source state.
- **`None`** — skip the reconciliation refresh. Use only when the adapter
  buffers events for late subscribers (e.g., a `MutableSharedFlow` with
  `replay = Int.MAX_VALUE` or a "snapshot then subscribe" primitive).

### `UnknownItemPolicy`

Controls what happens when an `Updated`/`Removed`/`Moved` event (or an
`*Identity` insert anchor) names an item that is not in any cached page —
typically because it lives outside the visible window:

- **`Drop` (default)** — silently ignore the event. Correct for items
  outside the window.
- **`RefreshAll`** — escalate to a full `refreshAll()`. Use when the source
  can hand the paginator an event for an item that *should* be visible but
  is not, indicating cache drift.

> There is intentionally no "refresh just the boundary pages" middle option.
> Paginator is offset-based: inserting one row in the source shifts every
> following row by one position globally, so refreshing only the first and
> last pages leaves the cached middle pages inconsistent (rows missing or
> duplicated at page boundaries). The honest choices are `Drop` (lose the
> event) or `RefreshAll` (full refetch). For granular Tier 2, the right
> answer is to split events into `Created` / `Updated` at the repository
> level — see Tier 2 below.

### `initPageState` — overflow page creation

Controls what happens when an `Inserted` (or the insert half of a `Moved`)
overflows the **last** cached page — the new item pushed past capacity has
nowhere to land unless a trailing page is created.

- **Default (a factory is supplied)** — a new trailing page is created so the
  overflowed item is **not dropped**. The page is the **same class** as the
  page that overflowed (a custom `OffsetPageState` subclass is preserved) and
  gets a fresh id, via the configured `core.initializer*Page` factories. This
  is the same default the CRUD `addElement` / `addAllElements` family uses, so
  reactive inserts and direct edits behave identically.
- **Custom factory** — pass your own `(page, data) -> OffsetPageState<T>` to
  decide exactly how the trailing page is built.
- **`null` (opt out)** — overflow past the last page is **dropped**, matching
  the pre-overflow-algorithm behaviour. Use this when the last cached page is
  the genuine end of the list and you would rather drop than grow the cache
  off-screen.

```kotlin
paginator.observe(
    scope = viewModelScope,
    source = source,
    initPageState = null,          // drop tail overflow instead of creating a page
)
```

> This governs **end overflow only**. An explicit `InsertPosition.At` that
> points to an **uncached** page is always treated as out-of-window (deferred
> to `UnknownItemPolicy`) — the factory never materialises an arbitrary far
> page, which would create a non-contiguous island in the cache.

## Adapter Recipes

Three tiers of adapter, ordered by effort and granularity. Pick the
simplest one that meets your performance needs — coarse `Invalidate`
works for most apps; you only need fine-grained events when the visible
list is large or changes are frequent.

### Tier 1 — Coarse Invalidation (simplest)

Use when: the visible page count is small, you don't care about per-row
optimisation, and you want zero coupling between your write paths and
the paginator.

The adapter just listens for "anything in this table changed" and asks
the paginator to refresh every loaded page.

```kotlin
// Domain
data class User(val id: Long, val name: String, val email: String)

// Adapter — uses Room's invalidation tracker directly.
class UserReactiveCache(
    private val db: AppDatabase,
) : PaginatorReactiveCache<User, Long> {

    override fun identity(item: User): Long = item.id

    override fun changes(): Flow<ReactiveEvent<User, Long>> =
        db.invalidationTrackerFlow("users")
            .map { ReactiveEvent.Invalidate }
}

// Helper that turns Room's InvalidationTracker callback into a Flow.
fun RoomDatabase.invalidationTrackerFlow(vararg tables: String): Flow<Unit> =
    callbackFlow {
        val observer = object : InvalidationTracker.Observer(tables) {
            override fun onInvalidated(tables: Set<String>) {
                trySend(Unit)
            }
        }
        invalidationTracker.addObserver(observer)
        awaitClose { invalidationTracker.removeObserver(observer) }
    }
```

Wiring:

```kotlin
class UserListViewModel(dao: UserDao, db: AppDatabase) : ViewModel() {
    val paginator = mutablePaginator<User> {
        capacity = 20
        load { page -> dao.getPage(limit = capacity, offset = (page - 1) * capacity) }
    }.also { p ->
        p.observe(scope = viewModelScope, source = UserReactiveCache(db))
    }
}
```

Every write to the `users` table — your own or a background sync's —
triggers `refreshAll()`. With `capacity = 20` and 3 loaded pages, that's
3 DAO queries per change. Acceptable for most CRUD-style UIs.

### Tier 2 — Domain Event Bus (granular, app-level discipline)

Use when: you control all write paths to the database and want only the
exact rows that changed to be re-rendered.

You publish a typed event from the same transaction that mutates the
database. The adapter just relays those events.

```kotlin
// 1) Typed domain events.
sealed interface UserChange {
    data class Saved(val user: User) : UserChange   // insert OR update
    data class Deleted(val id: Long) : UserChange
}

// 2) Repository owns the bus.
class UserRepository(
    private val db: AppDatabase,
    private val dao: UserDao,
) {
    private val _changes = MutableSharedFlow<UserChange>(extraBufferCapacity = 64)
    val changes: SharedFlow<UserChange> = _changes.asSharedFlow()

    suspend fun upsert(user: User) = db.withTransaction {
        dao.upsert(user)
        _changes.emit(UserChange.Saved(user))
    }

    suspend fun delete(id: Long) = db.withTransaction {
        dao.deleteById(id)
        _changes.emit(UserChange.Deleted(id))
    }
}

// 3) Adapter that maps domain events to ReactiveEvents.
//    Note: the repo must already know whether a Saved is an insert or
//    an update — track that yourself if you need Inserted vs Updated.
class UserReactiveCache(
    private val repository: UserRepository,
) : PaginatorReactiveCache<User, Long> {

    override fun identity(item: User): Long = item.id

    override fun changes(): Flow<ReactiveEvent<User, Long>> =
        repository.changes.map { change ->
            when (change) {
                is UserChange.Saved -> ReactiveEvent.Updated(change.user)
                is UserChange.Deleted -> ReactiveEvent.Removed(change.id)
            }
        }
}
```

**Catch:** the example treats every `Saved` as `Updated`. If the user is
not currently cached, the paginator drops the event (per
`UnknownItemPolicy.Drop`). That's wrong for *brand-new* users that
should appear in the visible window. Two fixes:

1. **Split the event** in the repository: `Created(user)` vs
   `Updated(user)`, then map `Created` to `ReactiveEvent.Inserted(...,
   InsertPosition.Tail)` (or wherever your sort order puts new rows).
   Precise and cheap at steady state — recommended.
2. **Use `UnknownItemPolicy.RefreshAll`** — every "unknown" target
   escalates to a full refresh. No event-splitting needed but costs one
   load per cached page on every missed insert; only acceptable when the
   visible window is one or two pages.

> There is no in-between "refresh just the affected page" option. Inserting
> one row globally shifts every following row by one — refreshing a subset
> of pages would leave the rest of the cache inconsistent. The choice is
> precise (split events) or full (`RefreshAll`).

### Tier 3 — Snapshot Diffing (granular, no app-level discipline)

Use when: the DAO exposes `Flow<List<T>>` for the whole table (or the
relevant slice) and you don't want to instrument write sites.

Instead of hand-writing a diff, use the built-in
[
`SnapshotReactiveCache`](../paginator-core/src/commonMain/kotlin/com/jamal_aliev/paginator/core/cache/reactive/SnapshotReactiveCache.kt)
— the paginator analogue of RecyclerView's `ListAdapter` / `DiffUtil`. It
holds the previous snapshot, diffs each emission, and produces
`Inserted` / `Updated` / `Removed` (and optionally `Moved`) events for you.
You implement nothing — just point it at a `Flow<List<T>>` and an identity
selector:

```kotlin
val source = snapshotReactiveCache(
  snapshots = dao.observeAll(),   // Flow<List<User>>
  identity = { it.id },
)

paginator.observe(scope = viewModelScope, source = source)
```

The `DiffUtil` correspondence is one-to-one:

| RecyclerView                          | `snapshotReactiveCache`                       |
|---------------------------------------|-----------------------------------------------|
| `DiffUtil.areItemsTheSame(a, b)`      | `identity(a) == identity(b)`                  |
| `DiffUtil.areContentsTheSame(a, b)`   | `areContentsTheSame` param (default `a == b`) |
| `AsyncListDiffer.submitList(newList)` | a new emission on `snapshots`                 |
| RecyclerView animates the delta       | the CRUD                                      |

**Optional knobs:**

```kotlin
val source = snapshotReactiveCache(
  snapshots = dao.observeAll(),
  identity = { it.id },
  // Like DiffUtil.areContentsTheSame — return false to emit an Updated.
  // Use this to ignore volatile fields that should not trigger a re-render.
  areContentsTheSame = { old, new -> old.name == new.name && old.email == new.email },
  // How to handle a change in the relative order of surviving items.
  reorderPolicy = ReorderPolicy.Invalidate,
  // Where a new item goes — or null to skip the insert entirely (see below).
  resolveInsert = { _, leftNeighborId ->
    if (leftNeighborId == null) InsertPosition.Head
    else InsertPosition.AfterIdentity(leftNeighborId)
  },
)
```

**`ReorderPolicy`** governs only reordering of items that survive between two
snapshots — inserts, removals, and content edits are always precise point
events:

- **`Invalidate` (default)** — on a detected reorder, emit a single
  `Invalidate` (the paginator re-fetches every cached page; the
  source-of-truth ordering wins). Simplest and always correct, at the cost
  of per-row animation for the reordered items.
- **`Moves`** — emit `Moved` for the *minimal* set of items that actually
  changed position (the stable subsequence stays put). Precise animation,
  but every moved anchor must be inside the loaded window.

**`resolveInsert`** decides *where* a brand-new item lands — or whether it lands
at all. It receives the item and the identity of its left neighbour in the new
snapshot (`null` for the first item), and returns an `InsertPosition`, or `null`
to **veto** the insert. The default reproduces the snapshot order. Two common
overrides:

- **Newest-first feed whose reactive source is ordered the opposite way** to
  the paginator's pages (e.g. the DAO observes `ORDER BY … ASC` but `load`
  pages `DESC`). The cleanest fix is to reverse the snapshot upstream so the
  default still works — including for batch inserts —
  `snapshots = dao.observeAll().map { it.asReversed() }`. Forcing
  `{ _, _ -> InsertPosition.Head }` also works but mis-orders two new rows that
  arrive in the same emission.
- **Conditional / gated insert** — skip an insert when its target position is
  not currently valid. For example, a chat that opens on a middle page (newest
  page not loaded) must not prepend a live message to the wrong visible page:

  ```kotlin
  resolveInsert = { _, _ ->
      if (paginator.isNewestPageVisible()) InsertPosition.Head else null
  }
  ```

  A vetoed item stays out of the cache and is **not** routed through
  `UnknownItemPolicy` (the skip is deliberate). It surfaces later when the page
  it belongs to is loaded by `load`.

**First emission is a baseline.** The first snapshot only establishes the
diff baseline and emits nothing — initial population of the cache is the job
of `load` (plus the `observe()` `InitialSyncPolicy`). The snapshot stream
carries only *deltas* from then on. (This is why a naive hand-rolled diff
that compares the first snapshot against an empty list is unsafe: racing an
already-completed `load`, it would duplicate every visible row.)

**Trade-offs.** The diff keeps an in-memory copy of the previous snapshot, so
it scales with the snapshot size — not page count — and is O(N) per emission
(O(N²) on a reorder under `Moves`, for the LCS pass). For very large tables,
prefer Tier 2.

> ⚠️ **Windowing caveat.** Snapshot diffing assumes the snapshot fits inside
> the paginator's currently loaded window. If the snapshot is larger than the
> window, an `AfterIdentity(...)` anchor (for an insert or a `Moves` move) can
> point to a row that lives outside the cache — the event then falls through
> to `UnknownItemPolicy`. Ensure your DAO returns only the visible slice
> (`SELECT … LIMIT windowSize`), or accept that off-window inserts are dropped
> under `Drop` and escalate to a full refresh under `RefreshAll`.

#### Hybrid sources: `observe(deduplicateInserts = true)`

A common setup is **hybrid**: the `load` lambda fetches a page from REST and
writes it into the same local store the adapter observes (Room is the single
source of truth; `load` backfills it from the network). Those freshly written
rows then come *back* through the snapshot stream — and a naive diff would see
them as new and re-insert rows the paginator already has, duplicating them.

`observe()` guards against this by default:

```kotlin
paginator.observe(
  scope = viewModelScope,
  source = source,
  deduplicateInserts = true,   // default
)
```

When `deduplicateInserts` is on, an `Inserted` whose identity is **already**
cached is applied as an in-place update instead of a duplicate. This makes the
hybrid model work with zero extra bookkeeping — you do **not** need to track
"which rows did `load` already hand the paginator". Duplicate-by-identity
inserts are never correct, so the guard is on by default; pass `false` only if
you specifically want the literal "always insert" behaviour.

> Together, `resolveInsert` (position + veto) and `deduplicateInserts` (hybrid
> de-duplication) let `SnapshotReactiveCache` cover the demanding cases — a
> newest-first chat with live pushes, jump-to-unread, and a REST→Room→paginator
> backfill — without a hand-written adapter.

#### Under the hood / full control

`SnapshotReactiveCache` is a regular `PaginatorReactiveCache` — if you need
behaviour beyond what `areContentsTheSame` / `reorderPolicy` / `resolveInsert`
expose, implement `changes()` yourself with the same shape:

```kotlin
class UserReactiveCache(
    private val dao: UserDao,
) : PaginatorReactiveCache<User, Long> {

    override fun identity(item: User): Long = item.id

    override fun changes(): Flow<ReactiveEvent<User, Long>> = flow {
      var previous: Map<Long, User>? = null   // null until the baseline lands
        dao.observeAll().collect { snapshot ->
            val current: Map<Long, User> = snapshot.associateBy { it.id }
          val before = previous
          previous = current
          if (before == null) return@collect   // first snapshot = baseline only

          val batch = mutableListOf<ReactiveEvent<User, Long>>()
          for ((id, _) in before) {
                if (id !in current) batch += ReactiveEvent.Removed(id)
            }
            snapshot.forEachIndexed { index, user ->
              val prior = before[user.id]
                when {
                  prior == null -> batch += ReactiveEvent.Inserted(
                        item = user,
                    position = if (index == 0) InsertPosition.Head
                    else InsertPosition.AfterIdentity(snapshot[index - 1].id),
                    )
                  prior != user -> batch += ReactiveEvent.Updated(user)
                }
            }

          when (batch.size) {
            0 -> Unit
            1 -> emit(batch.single())
            else -> emit(ReactiveEvent.Batch(batch))
          }
        }
    }
}
```

`emit(ReactiveEvent.Batch(...))` makes the paginator apply the diff
inside a single `transaction { ... }` — the L1 cache either reflects
the new snapshot fully or is rolled back to the previous one.

## Worked Examples per Event

These show each `ReactiveEvent` variant in a realistic scenario. The
source code for the adapter side is omitted — pick a tier from above and
emit the event shown.

### `Updated` — patch a single field

A user edits their display name. The row's id stays the same; only
fields change.

```kotlin
// Source side (your repo / event bus):
repository.emit(UserChange.Updated(currentUser.copy(name = "Jamal A.")))

// Adapter side:
ReactiveEvent.Updated(item = User(id = 42L, name = "Jamal A.", ...))
```

What the paginator does: finds the cached `User` whose `identity` is
`42L`, replaces it in place. The position doesn't move. If `id = 42L` is
not currently cached (it's outside the visible window), the event is
dropped under `UnknownItemPolicy.Drop`.

### `Removed` — delete one item, the rest shift up

The user deletes a contact. The contact is currently visible.

```kotlin
ReactiveEvent.Removed(identity = 42L)
```

What the paginator does: finds the cached item with `id = 42L`, removes
it from its page. Because removal would leave the page short of capacity,
the paginator pulls the first item from the next cached page to fill the
gap. If the next page is also cached, the cascade continues. The visible
list looks like a true delete with everything shifting up by one.

### `Inserted` + `Head` — new chat message at the top

A "newest first" feed (chats, notifications). A new message arrives via
WebSocket.

```kotlin
ReactiveEvent.Inserted(
    item = Message(id = 999L, body = "hi", createdAt = now()),
    position = InsertPosition.Head,
)
```

What the paginator does: inserts at the start of the first cached page.
The previous head item is pushed to index 1, the last item of that page
cascades into the start of page 2, and so on. The visible list grows by
one item at the top.

### `Inserted` + `Tail` — append to an infinite log

A "oldest first" feed (activity log, transaction history). A new entry
is appended.

```kotlin
ReactiveEvent.Inserted(
    item = LogEntry(id = 1000L, message = "user signed in", at = now()),
    position = InsertPosition.Tail,
)
```

What the paginator does: appends to the end of the last cached page.
If that page was already at capacity, the new item creates a fresh page
beyond it (controlled by [`initPageState`](#initpagestate--overflow-page-creation);
pass `null` to drop the overflow instead). The visible list grows by one item
at the bottom.

### `Inserted` + `AfterIdentity` — a reply lands right after its parent

A threaded comments feed. A new reply to comment `42L` should appear
immediately below it.

```kotlin
ReactiveEvent.Inserted(
    item = Comment(id = 77L, parentId = 42L, body = "+1"),
    position = InsertPosition.AfterIdentity(identity = 42L),
)
```

What the paginator does: finds the cached comment with `id = 42L`,
inserts the new comment one slot to its right. Subsequent items on the
same page cascade forward by one; the tail of the page may overflow
into the next page.

If `id = 42L` is not currently cached, the new comment cannot be
positioned and the event is dropped (under `UnknownItemPolicy.Drop`) or
escalated to `refreshAll()` (under `UnknownItemPolicy.RefreshAll`).

### `Inserted` + `At` — explicit coordinate (rare)

An admin tool inserts an item at a specific known position — say, the
top of page 3 — and you really do mean that exact coordinate.

```kotlin
ReactiveEvent.Inserted(
    item = item,
    position = InsertPosition.At(page = 3, index = 0),
)
```

What the paginator does: inserts at `(3, 0)` if page 3 is cached;
otherwise drops the event (no page to insert into). Note that `At`
references survive page rebalancing badly — if a `Removed` event a
moment earlier caused pages to shift, your coordinate now points
somewhere else. Prefer `AfterIdentity` / `BeforeIdentity` for anything
data-driven.

### `Moved` — an item changes position (drag-to-reorder, sort change)

A user drags a task above its sibling, or a backend re-ranks a feed item.
The item itself may also have new field values — `Moved` carries the
fresh item, so it doubles as an `Updated` at the same time.

```kotlin
ReactiveEvent.Moved(
    item = task.copy(priority = HIGH),
    position = InsertPosition.AfterIdentity(identity = anchorTaskId),
)
```

What the paginator does: opens a transaction, removes the cached item
with the same identity, inserts the new item at `position`. If either
step fails (anchor not cached, position unresolvable), the transaction
rolls back so the UI never observes a half-applied move.

If the item being moved is not currently cached, the active
`UnknownItemPolicy` decides whether to drop or refresh.

### `Invalidate` — when in doubt

The source signals "something changed but I can't describe it
precisely" — a bulk truncate, a foreign-key cascade delete, a sync
job that rewrote half the table.

```kotlin
ReactiveEvent.Invalidate
```

What the paginator does: runs `refreshAll()`, re-fetching every
currently cached page via `load`. Expensive but always correct.

This is also the right fallback inside an adapter whenever you can't
compute a precise event — see Tier 1 above.

### `Batch` — atomically apply a transaction's effects

The repo runs a transaction that moves an item from list A to list B,
plus updates one of B's existing items. You want the visible state to
either reflect the whole transaction or none of it — never a half-
applied state.

```kotlin
ReactiveEvent.Batch(
    events = listOf(
        ReactiveEvent.Removed(identity = 7L),
        ReactiveEvent.Inserted(
            item = movedItem,
            position = InsertPosition.AfterIdentity(identity = 10L),
        ),
        ReactiveEvent.Updated(item = neighbour),
    ),
)
```

What the paginator does: wraps applying all three events in
`paginator.transaction { ... }`. If any sub-event throws, the L1 cache
is rolled back to the state it had before the batch — none of the three
appear. Batches applied recursively inside the same transaction: a
nested `Batch` element joins the surrounding transaction rather than
opening a new one, so flattening the tree of batches yourself or letting
the paginator recurse yields the same effect.

## Lifecycle & Cancellation

`observe()` returns the `Job` that owns the subscription. **You** decide
when it dies.

```kotlin
// ViewModel — easiest case. Subscription lives as long as the ViewModel.
class FeedViewModel(...) : ViewModel() {
    private val paginator = mutablePaginator<Post> { … }

    init {
        paginator.observe(scope = viewModelScope, source = postsCache)
    }
    // No manual cancel needed — viewModelScope cancels in onCleared().
}

// Compose — subscription tied to a Composable's lifetime.
@Composable
fun FeedScreen(viewModel: FeedViewModel = viewModel()) {
    LaunchedEffect(viewModel) {
        // Re-subscribes if viewModel changes; cancels on disposal.
        // Note: if the ViewModel already subscribed in init, do NOT
        // resubscribe here — it would throw on the active-subscription guard.
    }
}

// Lifecycle-aware (e.g., pause while screen is in background).
class FeedFragment : Fragment() {
    private val viewModel: FeedViewModel by viewModels()
    private var job: Job? = null

    override fun onStart() {
        super.onStart()
        job = viewModel.paginator.observe(
            scope = lifecycleScope,
            source = viewModel.source,
        )
    }
    override fun onStop() {
        super.onStop()
        job?.cancel(); job = null
    }
}
```

Key contract points:

- The paginator does **not** own the `Job`. A paginator can outlive any
  subscription.
- **At most one active subscription per paginator.** The second concurrent
  `observe()` throws `IllegalStateException` — cancel the first one before
  re-subscribing.
- Cancellation is destructive: re-subscribing pays the `InitialSyncPolicy`
  cost again. Don't toggle observe()/cancel() per UI event; cancel only at
  real lifecycle boundaries.

## Testing Your Adapter

The straightforward pattern is to drive a `MutableSharedFlow` from the test
body and assert on the paginator's cache. Set `replay` high enough that
emissions made *before* the test dispatches the `observe()` coroutine still
arrive once the collector subscribes — this is a test-runner artefact, not
something real Room/SQLDelight adapters need:

```kotlin
private class FakeReactiveCache : PaginatorReactiveCache<Item, Long> {
    // replay = 64: tests emit before the collector starts; real adapters
    // (Room, SQLDelight, WebSocket) collect eagerly and don't need replay.
    private val events = MutableSharedFlow<ReactiveEvent<Item, Long>>(replay = 64)
    override fun identity(item: Item): Long = item.id
    override fun changes(): Flow<ReactiveEvent<Item, Long>> = events.asSharedFlow()
    suspend fun emit(event: ReactiveEvent<Item, Long>) = events.emit(event)
}

@Test
fun `Updated event replaces matching item by identity`() = runTest {
    val paginator = populatedPaginator()  // load a couple of pages first
    val source = FakeReactiveCache()
    val job = paginator.observe(
        scope = this,
        source = source,
        initialSync = InitialSyncPolicy.None,
    )

    source.emit(ReactiveEvent.Updated(Item(id = 5L, label = "patched")))
    runCurrent()  // let the collector consume

    assertEquals("patched", paginator.cache.getStateOf(2)!!.data.first { it.id == 5L }.label)
    job.cancel()
}
```

The same shape works for `Inserted`, `Removed`, `Moved`, `Batch`,
`Invalidate`, and for asserting unknown-item policies. See
[
`PaginatorReactiveObserveTest`](../paginator-offset/src/commonTest/kotlin/com/jamal_aliev/paginator/offset/PaginatorReactiveObserveTest.kt)
for the full suite.

## Persistent Cache Interaction

The L2 [`PersistentPagingCache`](6.%20caching.md#persistent-cache-l2) is
**deprecated since 10.3.0** and is not supported together with reactive
sources. When the reactive source *is* the local database, L2 is redundant
anyway — the database already plays that role — and `observe()` logs a
warning if both are configured. Drop the `PersistentPagingCache` and keep the
database as the single source of truth: the `load` lambda writes fetched pages
into the database, and the reactive source brings them into the paginator.

## Operational Notes

- **Identity must be stable.** `identity(item)` is the join key the paginator
  uses to find cached items. If your domain object's `equals` changes when a
  field is edited, never use `equals`-based identity — return the primary
  key.
- **Pick the right `ID` type.** The `<T, ID : Any>` parameter on
  `PaginatorReactiveCache` pins the identity type at compile time. With Room
  `Long` PKs you write `PaginatorReactiveCache<User, Long>`, and the compiler
  now rejects `Removed(42)` against a `Long`-typed key (the unparametrised
  earlier design accepted it as `Any` and the equality check silently
  failed). Use `Long`, `String`, or a dedicated id `data class` — anything
  with meaningful `equals`/`hashCode`.
- **Insert correctness is the adapter's responsibility.** The paginator
  cannot validate that `InsertPosition.AfterIdentity(x)` actually puts the
  item in the right sort order; the adapter must.
- **Events are not infinitely buffered.** `observe()` collects from
  `changes()` as soon as the launched job is dispatched. If your adapter
  emits events before subscribers arrive and the underlying flow has no
  replay buffer, those events are lost. Choose a flow shape that matches
  your concurrency model — `MutableSharedFlow(replay = ...)`, a Channel-
  backed flow, or rely on `InitialSyncPolicy.RefreshAll` to reconcile.
- **Backpressure is on the source side.** The paginator collects serially
  but does not throttle the producer. With a chatty source (e.g., a
  WebSocket emitting per-keystroke deltas, or an `Invalidate` storm during
  a sync), pick the right overflow strategy on the producing flow:
    - `MutableSharedFlow(extraBufferCapacity = N, onBufferOverflow = SUSPEND)`
      backpressures the producer — safe default for DB writes you control.
    - `BufferOverflow.DROP_OLDEST` is dangerous for `Removed`/`Inserted` (you
      lose causal events) but fine for collapsing repeated `Invalidate`s.
    - Combine bursts of related events into a single `ReactiveEvent.Batch`
      upstream — fewer transactions, less per-event overhead.
- **Errors don't kill the subscription.** Exceptions during event
  application are routed to `onError` (default: log at warn). Pass
  `onError = { throw it }` to fail the subscription job on first error.
- **Batch what comes from one transaction.** If a single source-of-truth
  transaction produces multiple changes, emit them as one
  `ReactiveEvent.Batch(...)` — not as separate events spaced out in
  time. The paginator then renders the transaction atomically; in
  between events your UI would briefly show a half-applied state.

## Cursor Paginator

Everything above applies to the **offset** paginator
([
`MutablePaginator<T>`](../paginator-offset/src/commonMain/kotlin/com/jamal_aliev/paginator/offset/MutablePaginator.kt)).
The **cursor** paginator
([
`MutableCursorPaginator<String, T>`](../paginator-cursor/src/commonMain/kotlin/com/jamal_aliev/paginator/cursor/MutableCursorPaginator.kt))
ships its own, parallel reactive surface in `paginator-cursor` — same
shape, same policies, only the types and the insert-position semantics
differ (because cursor pages are addressed by an opaque `self` key, not by
a numeric page index).

### API parallel

| Offset (paginator-offset)                                                                       | Cursor (paginator-cursor)                                                                             |
|-------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------|
| `MutablePaginator<T>.observe(scope, source, ...)`                                               | `MutableCursorPaginator<String, T>.observe(scope, source, ...)`                                       |
| `PaginatorReactiveCache<T, ID>`                                                                 | `CursorPaginatorReactiveCache<T, ID>`                                                                 |
| `ReactiveEvent<T, ID>` (`Updated` / `Removed` / `Inserted` / `Moved` / `Invalidate` / `Batch`)  | `CursorReactiveEvent<T, ID>` (same variants)                                                          |
| `InsertPosition<ID>` (`Head` / `Tail` / `At(page, index)` / `AfterIdentity` / `BeforeIdentity`) | `CursorInsertPosition<ID>` (`Head` / `Tail` / `At(self, index)` / `AfterIdentity` / `BeforeIdentity`) |
| `SnapshotReactiveCache` / `snapshotReactiveCache(...)`                                          | `CursorSnapshotReactiveCache` / `cursorSnapshotReactiveCache(...)`                                    |
| `InitialSyncPolicy`, `UnknownItemPolicy`, `ReorderPolicy`                                       | reused from `paginator-core` — same enum values                                                       |
| `observe(..., deduplicateInserts = true)`, `resolveInsert` on the snapshot cache                | identical                                                                                             |

The wiring, lifecycle, single-subscription guard, persistent-cache warning,
`onError` semantics, the built-in snapshot-diffing cache (`Tier 3`), the
`deduplicateInserts` guard, and the `resolveInsert` knob are all identical. If
you already understand the offset surface, the cursor surface has no new
concepts — only renamed types.

The built-in DiffUtil-style cache ports one-for-one — give it a
`Flow<List<T>>` and an identity selector:

```kotlin
val source = cursorSnapshotReactiveCache(
  snapshots = dao.observeAll(),   // Flow<List<Message>>
  identity = { it.id },
)
paginator.observe(scope = viewModelScope, source = source)
```

```kotlin
class MessageReactiveCache(dao: MessageDao) : CursorPaginatorReactiveCache<Message, Long> {
    override fun identity(item: Message): Long = item.id
    override fun changes(): Flow<CursorReactiveEvent<Message, Long>> = dao.observeChanges()
}

val paginator = mutableCursorPaginator<String, Message> {
    capacity = 20
    load { cursor -> api.fetchPage(cursor?.self as String?) }
}

val subscription: Job = paginator.observe(
    scope = viewModelScope,
    source = MessageReactiveCache(dao),
    initialSync = InitialSyncPolicy.RefreshAll,
    unknownItem = UnknownItemPolicy.Drop,
)
```

### `CursorInsertPosition`

The only structural difference from the offset variant is `At` — cursor
pages are keyed by an `Any` `self` (typically a string token from the
backend), not by a numeric index, so the coordinate becomes
`At(self, index)`:

| Position                 | Cursor mapping                                                                                                                                                                                                                                           |
|--------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `Head`                   | Prepend to the head cached page (`core.headCursor()`).                                                                                                                                                                                                   |
| `Tail`                   | Append to the tail cached page (`core.tailCursor()`).                                                                                                                                                                                                    |
| `At(self, index)`        | Insert at `(self, index)` on the page identified by `self`. Dropped when `self` is not in the cache (no synthesis — the cursor paginator never invents a missing page on insert; see [tail-insert overflow caveat](#tail-insert-overflow-caveat) below). |
| `AfterIdentity(anchor)`  | Insert immediately after the cached item with `identity == anchor`.                                                                                                                                                                                      |
| `BeforeIdentity(anchor)` | Insert immediately before the cached item with `identity == anchor`.                                                                                                                                                                                     |

`Head` / `Tail` / `AfterIdentity` / `BeforeIdentity` behave exactly like
the offset versions — cascade rules and `UnknownItemPolicy` apply the
same way.

### Tail-insert overflow caveat

`MutableCursorPaginator.addAllElements(...)` accepts an optional
[
`CursorBookmarkFactory`](../paginator-cursor/src/commonMain/kotlin/com/jamal_aliev/paginator/cursor/MutableCursorPaginator.kt)
so that overflow past the tail page can mint a brand-new tail page
on the fly. The cursor `observe()` now **exposes** that factory (plus an
`initPageState` for the new page's state), threaded through to every
insert route — so you can opt into tail-page creation on the reactive
path too:

```kotlin
paginator.observe(
    scope = viewModelScope,
    source = source,
    bookmarkFactory = { overflowIndex, previous ->
        // Mint the new tail `self`. Only you know how — it's server-issued.
        CursorBookmark(prev = previous.self, self = newSelfFor(previous), next = null)
    },
)
```

**The factory still defaults to `null`,** and that default matters: unlike
the offset paginator, the cursor paginator cannot *invent* a `self` key.
So with no `bookmarkFactory`, an `Inserted(item, Tail)` (or any insert
that cascades past the tail) on a full tail page drops the overflow —
the same as calling the CRUD `addElement` without a factory. When you
*do* supply one, `initPageState` defaults to the same-class factory
([`defaultCursorOverflowPageFactory`]) so the new page mirrors the page
that overflowed.

When you can't (or don't want to) mint a `self`, two alternatives:

1. **Pre-emit `Invalidate`** before the inserts — the next navigation
   will fetch the real new tail page from the server, with the
   server-assigned `self`.
2. **Insert before a known anchor** instead of at `Tail` —
   `AfterIdentity(lastVisibleId)` lands the row above the tail boundary
   and the existing items cascade forward into the (cached) next page,
   not into a hypothetical new one.

The offset paginator makes tail creation the *default* because new pages
are addressable by a deterministic next integer; cursors are
server-issued and therefore unsynthesisable from the client side, which
is why the cursor factory stays opt-in.

### Adapter example

Tier 2 (domain event bus) for a `Message` feed keyed by `Long`:

```kotlin
// 1) Typed domain events.
sealed interface MessageChange {
    data class Sent(val message: Message) : MessageChange   // brand-new
    data class Edited(val message: Message) : MessageChange
    data class Deleted(val id: Long) : MessageChange
}

// 2) Repository owns the bus.
class MessageRepository(private val dao: MessageDao) {
    private val _changes = MutableSharedFlow<MessageChange>(extraBufferCapacity = 64)
    val changes: SharedFlow<MessageChange> = _changes.asSharedFlow()

    suspend fun send(message: Message) {
        dao.insert(message)
        _changes.emit(MessageChange.Sent(message))
    }
    suspend fun edit(message: Message) {
        dao.update(message)
        _changes.emit(MessageChange.Edited(message))
    }
    suspend fun delete(id: Long) {
        dao.delete(id)
        _changes.emit(MessageChange.Deleted(id))
    }
}

// 3) Adapter that maps domain events to CursorReactiveEvents.
class MessageReactiveCache(
    private val repository: MessageRepository,
) : CursorPaginatorReactiveCache<Message, Long> {

    override fun identity(item: Message): Long = item.id

    override fun changes(): Flow<CursorReactiveEvent<Message, Long>> =
        repository.changes.map { change ->
            when (change) {
                is MessageChange.Sent ->
                    CursorReactiveEvent.Inserted(change.message, CursorInsertPosition.Head)
                is MessageChange.Edited ->
                    CursorReactiveEvent.Updated(change.message)
                is MessageChange.Deleted ->
                    CursorReactiveEvent.Removed(change.id)
            }
        }
}
```

The Tier 1 (coarse `Invalidate`) and Tier 3 (snapshot diffing) recipes
shown earlier translate one-for-one — replace `ReactiveEvent` with
`CursorReactiveEvent`, `InsertPosition` with `CursorInsertPosition`, and
`PaginatorReactiveCache` with `CursorPaginatorReactiveCache`. For Tier 3
there is nothing to translate by hand: use the built-in
`cursorSnapshotReactiveCache(...)` (the cursor twin of
`snapshotReactiveCache`), which exposes the same `areContentsTheSame`,
`reorderPolicy`, and `resolveInsert` knobs. Everything else (lifecycle, error
handling, policies, `deduplicateInserts`, persistent-cache interaction,
testing patterns) carries over unchanged.
