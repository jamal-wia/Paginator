# Reactive Sources

[← Back to README](../README.md)

This page covers bridging the paginator to a **reactive source of truth** —
typically a local database (Room, SQLDelight, Realm), but also a WebSocket
feed, Server-Sent Events stream, in-app event bus, or any other source whose
contents change independently of the paginator's `load` lambda. The goal is
to keep the visible pages in sync with the source without re-fetching pages
on every mutation.

## API at a Glance

Two things to implement, one extension to call, one `Job` to cancel:

```kotlin
// 1) Implement the adapter — two methods.
class UserReactiveCache(dao: UserDao) : PaginatorReactiveCache<User, Long> {
    override fun identity(item: User): Long = item.id
    override fun changes(): Flow<ReactiveEvent<User, Long>> = dao.observeChanges()
}

// 2) Wire it to the paginator and keep the Job.
val job: Job = paginator.observe(
    scope = viewModelScope,
    source = UserReactiveCache(dao),
)

// 3) Cancel it when the consumer goes away.
override fun onCleared() {
    job.cancel()
}
```

Everything else on this page — events, positions, policies, adapter tiers —
fills in what `dao.observeChanges()` should actually emit and which
behavioural knobs you might want to turn.

## Data Flow

```
┌────────────┐    Flow<ReactiveEvent<T, ID>>    ┌─────────────┐    CRUD     ┌──────────┐
│  Source    │ ───────────────────────────────► │  observe()  │ ──────────► │  L1      │
│ (DAO, WS,  │                                  │  collector  │             │  cache   │ ──► UI
│  bus, …)   │                                  │             │             │          │
└────────────┘                                  └─────────────┘             └──────────┘
       ▲                                                                          │
       └────────── load(page)  (one-shot fetch, never invoked per-event) ─────────┘
```

The `load` lambda is still called for fresh pages (jump, paginate, refresh).
The reactive path is parallel — every event from `changes()` is translated to
a CRUD op on the L1 cache, *not* into a new `load`. The two paths converge in
the cache and the UI sees a single coherent state.

## The Antipattern: navigation from inside `load`

Do **not** call any navigation/refresh function from inside the `load`
lambda — `refresh`, `refreshAll`, `jump`, `jumpForward`, `jumpBack`,
`goNextPage`, `goPreviousPage`, `restart`, `saveState`, `restoreState`.

These all acquire `navigationMutex` at entry, and the outer call that
triggered your `load` already holds it. Since the mutex is non-reentrant,
the inner call will deadlock — your UI hangs with no error and no log.

CRUD operations (`setElement`, `removeElement`, `addAllElements` and the
extension helpers) do not take the mutex and are safe to call from inside
`load`.

For reactive sources, subscribe from *outside* `load` — see the next
section.

## The Solution: `observe()` + `PaginatorReactiveCache`

Subscribe to the reactive source from *outside* `load`, and let the
paginator translate each change to the matching CRUD operation:

```kotlin
val paginator = mutablePaginator<User> {
    capacity = 20
    load { page -> dao.getPage(page, capacity) }   // one-shot fetch
}

val subscription: Job = paginator.observe(
    scope = viewModelScope,
    source = UserReactiveCache(dao),               // implementations below
    initialSync = InitialSyncPolicy.RefreshAll,
    unknownItem = UnknownItemPolicy.Drop,
)
```

Cancel the returned `Job` when the consumer goes away (Activity destroy,
Composable disposal, ViewModel clear). The paginator does *not* own the
subscription's lifetime. See [Lifecycle & Cancellation](#lifecycle--cancellation).

> ⚠️ **One active subscription per paginator.** A second `observe()` call
> while a previous `Job` is still active throws `IllegalStateException`.
> Cancel the previous Job first. A completed/cancelled Job releases the slot
> automatically.

## Event Catalog

The adapter emits [
`ReactiveEvent<T, ID>`](../paginator/src/commonMain/kotlin/com/jamal_aliev/paginator/cache/reactive/ReactiveEvent.kt)
s
on its `changes()` flow. The paginator dispatches each event to the matching
CRUD operation:

| Event                      | What the paginator does                                                                           |
|----------------------------|---------------------------------------------------------------------------------------------------|
| `Updated(item)`            | Replaces the cached item whose `identity(cached) == identity(item)`.                              |
| `Removed(identity)`        | Removes the cached item with the matching identity (cascades from next page).                     |
| `Inserted(item, position)` | Inserts at the given [`InsertPosition`](#insert-positions); overflow cascades.                    |
| `Moved(item, position)`    | Transactional remove + insert at a new position. Doubles as `Updated` (item may have new fields). |
| `Invalidate`               | Runs `refreshAll()` — every cached page is re-fetched via `load`.                                 |
| `Batch(events)`            | Wraps applying the listed events in `transaction { … }` — all-or-nothing.                         |

Events are applied **in arrival order**. The paginator serialises application
internally, so adapters do not need to add their own synchronisation.

## Insert Positions

[
`InsertPosition<ID>`](../paginator/src/commonMain/kotlin/com/jamal_aliev/paginator/cache/reactive/InsertPosition.kt)
encodes where a new item lands. Pick the one that matches the source's
ordering:

| Position                 | When to use                                                                |
|--------------------------|----------------------------------------------------------------------------|
| `Head`                   | Newest-first feeds — every insert goes to position `(firstPage, 0)`.       |
| `Tail`                   | Oldest-first feeds — every insert goes to the end of the last cached page. |
| `At(page, index)`        | Absolute coordinate. Use sparingly; survives badly across page rebalance.  |
| `AfterIdentity(anchor)`  | Insert immediately after the item with `identity == anchor`.               |
| `BeforeIdentity(anchor)` | Insert immediately before the item with `identity == anchor`.              |

If the adapter cannot compute a meaningful position (e.g., a complex
`ORDER BY` it cannot mirror), emit `Invalidate` instead of guessing. The
paginator will run `refreshAll()` and the source-of-truth ordering wins.

## Policies

### `InitialSyncPolicy`

Controls what `observe()` does about the gap between the most recent page
load and the first observed event:

- **`RefreshAll` (default)** — issue `refreshAll()` immediately after
  subscribe. Costs one extra load per cached page, but eliminates the chance
  of missed updates that happened during the gap.
    - **No-op when the cache is empty at subscribe time** (you called
      `observe()` before any page had loaded). There is nothing to reconcile —
      the upcoming first `load()` will already see the latest source state.
- **`None`** — skip the reconciliation refresh. Use only when the adapter
  buffers events for late subscribers (e.g., a `MutableSharedFlow` with
  `replay = Int.MAX_VALUE` or a "snapshot then subscribe" primitive).

### `UnknownItemPolicy`

Controls what happens when an `Updated`/`Removed`/`Moved` event (or an
`*Identity` insert anchor) names an item that is not in any cached page —
typically because it lives outside the visible window:

- **`Drop` (default)** — silently ignore the event. Correct for items
  outside the window.
- **`RefreshAll`** — escalate to a full `refreshAll()`. Use when the source
  can hand the paginator an event for an item that *should* be visible but
  is not, indicating cache drift.

> There is intentionally no "refresh just the boundary pages" middle option.
> Paginator is offset-based: inserting one row in the source shifts every
> following row by one position globally, so refreshing only the first and
> last pages leaves the cached middle pages inconsistent (rows missing or
> duplicated at page boundaries). The honest choices are `Drop` (lose the
> event) or `RefreshAll` (full refetch). For granular Tier 2, the right
> answer is to split events into `Created` / `Updated` at the repository
> level — see Tier 2 below.

## Adapter Recipes

Three tiers of adapter, ordered by effort and granularity. Pick the
simplest one that meets your performance needs — coarse `Invalidate`
works for most apps; you only need fine-grained events when the visible
list is large or changes are frequent.

### Tier 1 — Coarse Invalidation (simplest)

Use when: the visible page count is small, you don't care about per-row
optimisation, and you want zero coupling between your write paths and
the paginator.

The adapter just listens for "anything in this table changed" and asks
the paginator to refresh every loaded page.

```kotlin
// Domain
data class User(val id: Long, val name: String, val email: String)

// Adapter — uses Room's invalidation tracker directly.
class UserReactiveCache(
    private val db: AppDatabase,
) : PaginatorReactiveCache<User, Long> {

    override fun identity(item: User): Long = item.id

    override fun changes(): Flow<ReactiveEvent<User, Long>> =
        db.invalidationTrackerFlow("users")
            .map { ReactiveEvent.Invalidate }
}

// Helper that turns Room's InvalidationTracker callback into a Flow.
fun RoomDatabase.invalidationTrackerFlow(vararg tables: String): Flow<Unit> =
    callbackFlow {
        val observer = object : InvalidationTracker.Observer(tables) {
            override fun onInvalidated(tables: Set<String>) {
                trySend(Unit)
            }
        }
        invalidationTracker.addObserver(observer)
        awaitClose { invalidationTracker.removeObserver(observer) }
    }
```

Wiring:

```kotlin
class UserListViewModel(dao: UserDao, db: AppDatabase) : ViewModel() {
    val paginator = mutablePaginator<User> {
        capacity = 20
        load { page -> dao.getPage(limit = capacity, offset = (page - 1) * capacity) }
    }.also { p ->
        p.observe(scope = viewModelScope, source = UserReactiveCache(db))
    }
}
```

Every write to the `users` table — your own or a background sync's —
triggers `refreshAll()`. With `capacity = 20` and 3 loaded pages, that's
3 DAO queries per change. Acceptable for most CRUD-style UIs.

### Tier 2 — Domain Event Bus (granular, app-level discipline)

Use when: you control all write paths to the database and want only the
exact rows that changed to be re-rendered.

You publish a typed event from the same transaction that mutates the
database. The adapter just relays those events.

```kotlin
// 1) Typed domain events.
sealed interface UserChange {
    data class Saved(val user: User) : UserChange   // insert OR update
    data class Deleted(val id: Long) : UserChange
}

// 2) Repository owns the bus.
class UserRepository(
    private val db: AppDatabase,
    private val dao: UserDao,
) {
    private val _changes = MutableSharedFlow<UserChange>(extraBufferCapacity = 64)
    val changes: SharedFlow<UserChange> = _changes.asSharedFlow()

    suspend fun upsert(user: User) = db.withTransaction {
        dao.upsert(user)
        _changes.emit(UserChange.Saved(user))
    }

    suspend fun delete(id: Long) = db.withTransaction {
        dao.deleteById(id)
        _changes.emit(UserChange.Deleted(id))
    }
}

// 3) Adapter that maps domain events to ReactiveEvents.
//    Note: the repo must already know whether a Saved is an insert or
//    an update — track that yourself if you need Inserted vs Updated.
class UserReactiveCache(
    private val repository: UserRepository,
) : PaginatorReactiveCache<User, Long> {

    override fun identity(item: User): Long = item.id

    override fun changes(): Flow<ReactiveEvent<User, Long>> =
        repository.changes.map { change ->
            when (change) {
                is UserChange.Saved -> ReactiveEvent.Updated(change.user)
                is UserChange.Deleted -> ReactiveEvent.Removed(change.id)
            }
        }
}
```

**Catch:** the example treats every `Saved` as `Updated`. If the user is
not currently cached, the paginator drops the event (per
`UnknownItemPolicy.Drop`). That's wrong for *brand-new* users that
should appear in the visible window. Two fixes:

1. **Split the event** in the repository: `Created(user)` vs
   `Updated(user)`, then map `Created` to `ReactiveEvent.Inserted(...,
   InsertPosition.Tail)` (or wherever your sort order puts new rows).
   Precise and cheap at steady state — recommended.
2. **Use `UnknownItemPolicy.RefreshAll`** — every "unknown" target
   escalates to a full refresh. No event-splitting needed but costs one
   load per cached page on every missed insert; only acceptable when the
   visible window is one or two pages.

> There is no in-between "refresh just the affected page" option. Inserting
> one row globally shifts every following row by one — refreshing a subset
> of pages would leave the rest of the cache inconsistent. The choice is
> precise (split events) or full (`RefreshAll`).

### Tier 3 — Snapshot Diffing (granular, no app-level discipline)

Use when: the DAO exposes `Flow<List<T>>` for the whole table (or the
relevant slice) and you don't want to instrument write sites.

The adapter holds the previous snapshot and diffs each emit, producing
`Inserted` / `Updated` / `Removed` events automatically.

```kotlin
class UserReactiveCache(
    private val dao: UserDao,
) : PaginatorReactiveCache<User, Long> {

    override fun identity(item: User): Long = item.id

    override fun changes(): Flow<ReactiveEvent<User, Long>> = flow {
        var previous: Map<Long, User> = emptyMap()
        dao.observeAll().collect { snapshot ->
            val current: Map<Long, User> = snapshot.associateBy { it.id }
            val batch = mutableListOf<ReactiveEvent<User, Long>>()

            // Removed = was in previous, not in current.
            for ((id, _) in previous) {
                if (id !in current) batch += ReactiveEvent.Removed(id)
            }
            // Inserted = in current, not in previous. Place by current index.
            // Updated  = in both, but differs.
            snapshot.forEachIndexed { index, user ->
                val before = previous[user.id]
                when {
                    before == null -> batch += ReactiveEvent.Inserted(
                        item = user,
                        position = inferInsertPosition(snapshot, index),
                    )
                    before != user -> batch += ReactiveEvent.Updated(user)
                }
            }

            if (batch.isNotEmpty()) emit(ReactiveEvent.Batch(batch))
            previous = current
        }
    }

    private fun inferInsertPosition(snapshot: List<User>, index: Int): InsertPosition<Long> =
        when {
            index == 0 -> InsertPosition.Head
            index == snapshot.lastIndex -> InsertPosition.Tail
            else -> InsertPosition.AfterIdentity(snapshot[index - 1].id)
        }
}
```

**Trade-offs.** The adapter keeps an in-memory map of every row, so it
scales with table size — not page count. It's also O(N) per snapshot.
For large tables, prefer Tier 2.

> ⚠️ **Windowing caveat.** Snapshot diffing assumes the *whole* table fits
> inside the paginator's currently loaded window. If the snapshot is larger
> than the window, an `AfterIdentity(snapshot[index - 1].id)` anchor can
> point to a row that lives outside the cache — the insert then falls
> through to `UnknownItemPolicy`. Ensure your DAO returns only the visible
> slice (`SELECT … LIMIT windowSize`), or accept that off-window inserts
> are dropped under `Drop` and escalate to a full refresh under
> `RefreshAll`.

`emit(ReactiveEvent.Batch(...))` makes the paginator apply the diff
inside a single `transaction { ... }` — the L1 cache either reflects
the new snapshot fully or is rolled back to the previous one.

## Worked Examples per Event

These show each `ReactiveEvent` variant in a realistic scenario. The
source code for the adapter side is omitted — pick a tier from above and
emit the event shown.

### `Updated` — patch a single field

A user edits their display name. The row's id stays the same; only
fields change.

```kotlin
// Source side (your repo / event bus):
repository.emit(UserChange.Updated(currentUser.copy(name = "Jamal A.")))

// Adapter side:
ReactiveEvent.Updated(item = User(id = 42L, name = "Jamal A.", ...))
```

What the paginator does: finds the cached `User` whose `identity` is
`42L`, replaces it in place. The position doesn't move. If `id = 42L` is
not currently cached (it's outside the visible window), the event is
dropped under `UnknownItemPolicy.Drop`.

### `Removed` — delete one item, the rest shift up

The user deletes a contact. The contact is currently visible.

```kotlin
ReactiveEvent.Removed(identity = 42L)
```

What the paginator does: finds the cached item with `id = 42L`, removes
it from its page. Because removal would leave the page short of capacity,
the paginator pulls the first item from the next cached page to fill the
gap. If the next page is also cached, the cascade continues. The visible
list looks like a true delete with everything shifting up by one.

### `Inserted` + `Head` — new chat message at the top

A "newest first" feed (chats, notifications). A new message arrives via
WebSocket.

```kotlin
ReactiveEvent.Inserted(
    item = Message(id = 999L, body = "hi", createdAt = now()),
    position = InsertPosition.Head,
)
```

What the paginator does: inserts at the start of the first cached page.
The previous head item is pushed to index 1, the last item of that page
cascades into the start of page 2, and so on. The visible list grows by
one item at the top.

### `Inserted` + `Tail` — append to an infinite log

A "oldest first" feed (activity log, transaction history). A new entry
is appended.

```kotlin
ReactiveEvent.Inserted(
    item = LogEntry(id = 1000L, message = "user signed in", at = now()),
    position = InsertPosition.Tail,
)
```

What the paginator does: appends to the end of the last cached page.
If that page was already at capacity, the new item creates a fresh page
beyond it. The visible list grows by one item at the bottom.

### `Inserted` + `AfterIdentity` — a reply lands right after its parent

A threaded comments feed. A new reply to comment `42L` should appear
immediately below it.

```kotlin
ReactiveEvent.Inserted(
    item = Comment(id = 77L, parentId = 42L, body = "+1"),
    position = InsertPosition.AfterIdentity(identity = 42L),
)
```

What the paginator does: finds the cached comment with `id = 42L`,
inserts the new comment one slot to its right. Subsequent items on the
same page cascade forward by one; the tail of the page may overflow
into the next page.

If `id = 42L` is not currently cached, the new comment cannot be
positioned and the event is dropped (under `UnknownItemPolicy.Drop`) or
escalated to `refreshAll()` (under `UnknownItemPolicy.RefreshAll`).

### `Inserted` + `At` — explicit coordinate (rare)

An admin tool inserts an item at a specific known position — say, the
top of page 3 — and you really do mean that exact coordinate.

```kotlin
ReactiveEvent.Inserted(
    item = item,
    position = InsertPosition.At(page = 3, index = 0),
)
```

What the paginator does: inserts at `(3, 0)` if page 3 is cached;
otherwise drops the event (no page to insert into). Note that `At`
references survive page rebalancing badly — if a `Removed` event a
moment earlier caused pages to shift, your coordinate now points
somewhere else. Prefer `AfterIdentity` / `BeforeIdentity` for anything
data-driven.

### `Moved` — an item changes position (drag-to-reorder, sort change)

A user drags a task above its sibling, or a backend re-ranks a feed item.
The item itself may also have new field values — `Moved` carries the
fresh item, so it doubles as an `Updated` at the same time.

```kotlin
ReactiveEvent.Moved(
    item = task.copy(priority = HIGH),
    position = InsertPosition.AfterIdentity(identity = anchorTaskId),
)
```

What the paginator does: opens a transaction, removes the cached item
with the same identity, inserts the new item at `position`. If either
step fails (anchor not cached, position unresolvable), the transaction
rolls back so the UI never observes a half-applied move.

If the item being moved is not currently cached, the active
`UnknownItemPolicy` decides whether to drop or refresh.

### `Invalidate` — when in doubt

The source signals "something changed but I can't describe it
precisely" — a bulk truncate, a foreign-key cascade delete, a sync
job that rewrote half the table.

```kotlin
ReactiveEvent.Invalidate
```

What the paginator does: runs `refreshAll()`, re-fetching every
currently cached page via `load`. Expensive but always correct.

This is also the right fallback inside an adapter whenever you can't
compute a precise event — see Tier 1 above.

### `Batch` — atomically apply a transaction's effects

The repo runs a transaction that moves an item from list A to list B,
plus updates one of B's existing items. You want the visible state to
either reflect the whole transaction or none of it — never a half-
applied state.

```kotlin
ReactiveEvent.Batch(
    events = listOf(
        ReactiveEvent.Removed(identity = 7L),
        ReactiveEvent.Inserted(
            item = movedItem,
            position = InsertPosition.AfterIdentity(identity = 10L),
        ),
        ReactiveEvent.Updated(item = neighbour),
    ),
)
```

What the paginator does: wraps applying all three events in
`paginator.transaction { ... }`. If any sub-event throws, the L1 cache
is rolled back to the state it had before the batch — none of the three
appear. Batches applied recursively inside the same transaction: a
nested `Batch` element joins the surrounding transaction rather than
opening a new one, so flattening the tree of batches yourself or letting
the paginator recurse yields the same effect.

## Lifecycle & Cancellation

`observe()` returns the `Job` that owns the subscription. **You** decide
when it dies.

```kotlin
// ViewModel — easiest case. Subscription lives as long as the ViewModel.
class FeedViewModel(...) : ViewModel() {
    private val paginator = mutablePaginator<Post> { … }

    init {
        paginator.observe(scope = viewModelScope, source = postsCache)
    }
    // No manual cancel needed — viewModelScope cancels in onCleared().
}

// Compose — subscription tied to a Composable's lifetime.
@Composable
fun FeedScreen(viewModel: FeedViewModel = viewModel()) {
    LaunchedEffect(viewModel) {
        // Re-subscribes if viewModel changes; cancels on disposal.
        // Note: if the ViewModel already subscribed in init, do NOT
        // resubscribe here — it would throw on the active-subscription guard.
    }
}

// Lifecycle-aware (e.g., pause while screen is in background).
class FeedFragment : Fragment() {
    private val viewModel: FeedViewModel by viewModels()
    private var job: Job? = null

    override fun onStart() {
        super.onStart()
        job = viewModel.paginator.observe(
            scope = lifecycleScope,
            source = viewModel.source,
        )
    }
    override fun onStop() {
        super.onStop()
        job?.cancel(); job = null
    }
}
```

Key contract points:

- The paginator does **not** own the `Job`. A paginator can outlive any
  subscription.
- **At most one active subscription per paginator.** The second concurrent
  `observe()` throws `IllegalStateException` — cancel the first one before
  re-subscribing.
- Cancellation is destructive: re-subscribing pays the `InitialSyncPolicy`
  cost again. Don't toggle observe()/cancel() per UI event; cancel only at
  real lifecycle boundaries.

## Testing Your Adapter

The straightforward pattern is to drive a `MutableSharedFlow` from the test
body and assert on the paginator's cache. Set `replay` high enough that
emissions made *before* the test dispatches the `observe()` coroutine still
arrive once the collector subscribes — this is a test-runner artefact, not
something real Room/SQLDelight adapters need:

```kotlin
private class FakeReactiveCache : PaginatorReactiveCache<Item, Long> {
    // replay = 64: tests emit before the collector starts; real adapters
    // (Room, SQLDelight, WebSocket) collect eagerly and don't need replay.
    private val events = MutableSharedFlow<ReactiveEvent<Item, Long>>(replay = 64)
    override fun identity(item: Item): Long = item.id
    override fun changes(): Flow<ReactiveEvent<Item, Long>> = events.asSharedFlow()
    suspend fun emit(event: ReactiveEvent<Item, Long>) = events.emit(event)
}

@Test
fun `Updated event replaces matching item by identity`() = runTest {
    val paginator = populatedPaginator()  // load a couple of pages first
    val source = FakeReactiveCache()
    val job = paginator.observe(
        scope = this,
        source = source,
        initialSync = InitialSyncPolicy.None,
    )

    source.emit(ReactiveEvent.Updated(Item(id = 5L, label = "patched")))
    runCurrent()  // let the collector consume

    assertEquals("patched", paginator.cache.getStateOf(2)!!.data.first { it.id == 5L }.label)
    job.cancel()
}
```

The same shape works for `Inserted`, `Removed`, `Moved`, `Batch`,
`Invalidate`, and for asserting unknown-item policies. See
[
`PaginatorReactiveObserveTest`](../paginator/src/commonTest/kotlin/com/jamal_aliev/paginator/PaginatorReactiveObserveTest.kt)
for the full suite.

## Persistent Cache Interaction

When the reactive source *is* the local database, the paginator's L2
[`PersistentPagingCache`](6.%20caching.md#persistent-cache-l2) becomes
redundant — the database already plays that role. `observe()` logs a
warning if both are configured. Pick one:

- **Database as source of truth (`observe`)** — drop the `PersistentPagingCache`.
- **REST as source of truth (`PersistentPagingCache`)** — don't use `observe`.

Stacking both works but writes the same data twice.

## Operational Notes

- **Identity must be stable.** `identity(item)` is the join key the paginator
  uses to find cached items. If your domain object's `equals` changes when a
  field is edited, never use `equals`-based identity — return the primary
  key.
- **Pick the right `ID` type.** The `<T, ID : Any>` parameter on
  `PaginatorReactiveCache` pins the identity type at compile time. With Room
  `Long` PKs you write `PaginatorReactiveCache<User, Long>`, and the compiler
  now rejects `Removed(42)` against a `Long`-typed key (the unparametrised
  earlier design accepted it as `Any` and the equality check silently
  failed). Use `Long`, `String`, or a dedicated id `data class` — anything
  with meaningful `equals`/`hashCode`.
- **Insert correctness is the adapter's responsibility.** The paginator
  cannot validate that `InsertPosition.AfterIdentity(x)` actually puts the
  item in the right sort order; the adapter must.
- **Events are not infinitely buffered.** `observe()` collects from
  `changes()` as soon as the launched job is dispatched. If your adapter
  emits events before subscribers arrive and the underlying flow has no
  replay buffer, those events are lost. Choose a flow shape that matches
  your concurrency model — `MutableSharedFlow(replay = ...)`, a Channel-
  backed flow, or rely on `InitialSyncPolicy.RefreshAll` to reconcile.
- **Backpressure is on the source side.** The paginator collects serially
  but does not throttle the producer. With a chatty source (e.g., a
  WebSocket emitting per-keystroke deltas, or an `Invalidate` storm during
  a sync), pick the right overflow strategy on the producing flow:
    - `MutableSharedFlow(extraBufferCapacity = N, onBufferOverflow = SUSPEND)`
      backpressures the producer — safe default for DB writes you control.
    - `BufferOverflow.DROP_OLDEST` is dangerous for `Removed`/`Inserted` (you
      lose causal events) but fine for collapsing repeated `Invalidate`s.
    - Combine bursts of related events into a single `ReactiveEvent.Batch`
      upstream — fewer transactions, less per-event overhead.
- **Errors don't kill the subscription.** Exceptions during event
  application are routed to `onError` (default: log at warn). Pass
  `onError = { throw it }` to fail the subscription job on first error.
- **Batch what comes from one transaction.** If a single source-of-truth
  transaction produces multiple changes, emit them as one
  `ReactiveEvent.Batch(...)` — not as separate events spaced out in
  time. The paginator then renders the transaction atomically; in
  between events your UI would briefly show a half-applied state.
