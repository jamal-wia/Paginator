## Cache Eviction Strategies

By default, `PagingCore` uses `InMemoryPagingCache` -- every loaded page stays in memory
forever. For long-lived paginators or memory-constrained environments, pass a
**cache strategy** via the `cache` parameter of `PagingCore`:

```kotlin
val paginator = MutablePaginator<Item>(
    core = PagingCore(cache = MostRecentPagingCache(maxSize = 50)),
    load = { page -> LoadResult(api.loadPage(page)) }
)
```

Available strategies:

| Strategy                   | Eviction rule                     | Key parameter   |
|----------------------------|-----------------------------------|-----------------|
| `InMemoryPagingCache`      | None -- unlimited cache           | --              |
| `MostRecentPagingCache`    | Least recently used page          | `maxSize`       |
| `QueuedPagingCache`        | First inserted page               | `maxSize`       |
| `TimeLimitedPagingCache`   | Pages older than TTL              | `ttl: Duration` |
| `ContextWindowPagingCache` | Everything outside context window | `margin`        |
| `NearestPagingCache`       | Page farthest from the page just loaded | `maxSize` |

### MostRecentPagingCache

Evicts the **least recently used** page when the cache exceeds `maxSize`. Both reads
(`getStateOf`, `getElement`) and writes (`setState`) count as "usage".

```kotlin
val paginator = MutablePaginator<Item>(
    core = PagingCore(
        cache = MostRecentPagingCache(
            maxSize = 50,                   // max pages in cache
            protectContextWindow = true,    // never evict visible pages (default)
        )
    ),
    load = { page -> LoadResult(api.loadPage(page)) }
)
```

| Parameter              | Default      | Description                                                   |
|------------------------|--------------|---------------------------------------------------------------|
| `maxSize`              | *(required)* | Maximum cached pages. Must be > 0                             |
| `protectContextWindow` | `true`       | Pages in `startContextPage..endContextPage` are never evicted; `maxSize` can then be exceeded, see [Protecting the Context Window](#protecting-the-context-window) |
| `evictionListener`     | `null`       | Callback when a page is evicted                               |

### QueuedPagingCache

Evicts the **oldest inserted** page when the cache exceeds `maxSize`. Unlike LRU, reading
a page does **not** change its eviction priority -- only the original insertion order matters.

```kotlin
val paginator = MutablePaginator<Item>(
    core = PagingCore(cache = QueuedPagingCache(maxSize = 30)),
    load = { page -> LoadResult(api.loadPage(page)) }
)
```

Parameters are the same as `MostRecentPagingCache`.

Overwriting a page that is still in the cache does not change its place in the queue. A page that
is **not** in the cache counts as a new insertion and goes to the end of the queue — also when it
had been in the cache before and another strategy of the chain removed it (see
[Composing Strategies](#composing-strategies)). The queue never evicts a page the cache does not
hold any more.

### TimeLimitedPagingCache

Evicts pages whose age exceeds a **time-to-live** duration. There is no `maxSize` --
the cache can hold any number of pages as long as they are fresh.

Expiry is checked **only when a page is written** (`setState`): there is no background timer, and
reading a page never evicts. Every `setState` of a page (re)starts that page's timer; reads restart
it only with `refreshOnAccess = true`, and untracked writes and reads never do (see
[Untracked access](#untracked-access--setstateuntracked--peekstateof)).

```kotlin
import kotlin.time.Duration.Companion.minutes

val paginator = MutablePaginator<Item>(
    core = PagingCore(
        cache = TimeLimitedPagingCache(
            ttl = 5.minutes,            // max page age
            refreshOnAccess = false,    // true = reading resets the timer
            protectContextWindow = true,
        )
    ),
    load = { page -> LoadResult(api.loadPage(page)) }
)
```

| Parameter              | Default                | Description                                                |
|------------------------|------------------------|------------------------------------------------------------|
| `ttl`                  | *(required)*           | Maximum page age. Must be positive                         |
| `refreshOnAccess`      | `false`                | If `true`, `getStateOf` / `getElement` reset the TTL timer |
| `protectContextWindow` | `true`                 | Expired pages in the context window are **kept**, so the window can show data older than `ttl`; `false` lets them expire like any other page |
| `timeSource`           | `TimeSource.Monotonic` | Override for deterministic testing                         |
| `evictionListener`     | `null`                 | Callback when a page is evicted                            |

### ContextWindowPagingCache

Keeps **only** pages within (or near) the current context window. After a `jump()` to a
distant page, the pages from the previous location are removed as soon as the next page is written
to the cache -- for an uncached target that is the target's own loading state, written right after
the window has moved. A `jump()` that is answered from the cache writes nothing, so the old pages
stay until the next write. This is the most aggressive strategy -- ideal for memory-constrained
environments.

```kotlin
val paginator = MutablePaginator<Item>(
    core = PagingCore(
        cache = ContextWindowPagingCache(
            margin = 2,   // keep 2 extra pages beyond each edge of the context window
        )
    ),
    load = { page -> LoadResult(api.loadPage(page)) }
)
```

| Parameter          | Default | Description                                              |
|--------------------|---------|----------------------------------------------------------|
| `margin`           | `0`     | Pages to keep beyond each edge. `0` = strict window only |
| `evictionListener` | `null`  | Callback when a page is evicted                          |

With `margin = 0`, the cache contains exactly `startContextPage..endContextPage`. With
`margin = 2`, it keeps `(startContextPage - 2)..(endContextPage + 2)`.

Things to know:

- There is **no** `protectContextWindow` parameter: the strategy *is* the window, so it never
  evicts a window page.
- It does **not limit the width** of the window. A window that grows by `goNextPage` keeps growing,
  and so does the cache. To bound the number of pages, use [`NearestPagingCache`](#nearestpagingcache)
  or combine it with a size-limiting strategy (see [Composing Strategies](#composing-strategies)).
- It evicts when a page is **written** (`setState`) and only while the paginator is started -- not
  at the moment the window moves. The page that is being written is never evicted by that write.

### NearestPagingCache

Keeps a **bounded window of the pages nearest to the page that was just loaded** and evicts the
farthest ones. It is made for bidirectional scrolling over a fixed number of pages -- a chat
history that holds three pages around the user, for example. Scroll forward and the farthest page
is the one behind you; scroll back and it is the one ahead.

```kotlin
val paginator = mutablePaginator<ChatMessage>(capacity = 20) {
    cache = NearestPagingCache(maxSize = 3)
    livePages(scope) { page -> observePage(page) }   // a page that leaves the cache ends its query
}
```

```
cached [1, 2, 3] + page 4 loaded  ->  [2, 3, 4]   // scrolled forward: page 1 is farthest
cached [2, 3, 4] + page 1 loaded  ->  [1, 2, 3]   // scrolled backward: page 4 is farthest
```

| Parameter          | Default      | Description                                        |
|--------------------|--------------|----------------------------------------------------|
| `maxSize`          | *(required)* | Pages to keep once a page has settled. Must be > 0 |
| `evictionListener` | `null`       | Callback when a page is evicted                    |

(The constructor also has a leading `cache` parameter, the inner cache to delegate to; it is
filled in by `+` and normally left alone, as with the other strategies.)

**When it evicts.** Only when a page **load completes**: a success (with or without data) is
written over the loading state of the same page, and the cache holds more than `maxSize` pages.
Navigation always writes the loading state of a page before it loads it, so this is exactly the
write that adds a freshly loaded page to the window. Everything else leaves the cache alone:

| Written state                                                        | Evicts down to `maxSize`? |
|----------------------------------------------------------------------|---------------------------|
| Success (also empty) over the page's loading state: a load completes | yes                       |
| Success over anything else (CRUD overflow page, promotion from L2)   | no                        |
| Loading (`Progress`)                                                 | no                        |
| Error                                                                | no                        |
| `setStateUntracked` / `peekStateOf`                                  | no                        |

That is what keeps an in-place edit safe: when a message is inserted into page 1 of a full window
and the overflow creates a new page at the end, the new page was not loaded, so nothing is evicted
and the page you just edited stays. A cancelled load that puts the previous success back over its
loading state looks like a completion; it evicts only if the cache is over `maxSize` at that moment.

Because loading and error pages never evict, the cache can **temporarily hold more than `maxSize`**
pages: the window plus one unfinished page on each edge, plus pages created by CRUD overflow. The
next completed load trims the excess, including unfinished pages that are far away.

**Which page goes first.** The page that has just been loaded (the *anchor*) is never evicted. The
other pages go in order of distance from it, farthest first, until the cache fits `maxSize`. At
equal distance a page **outside** the context window goes before one inside it; if the tie
remains, the page on the forward side (the higher page number) goes first. The listener is called
once per page that was really removed, starting with the farthest.

The rule looks only at which pages are cached right now. The strategy keeps **no state** of its
own: it does not depend on when pages were inserted or read, so scrolling in either direction never
punches a hole in the middle of the window.

**No `protectContextWindow`.** There is no such parameter, on purpose: the strategy is there to
trim the window, and protecting all of it would leave nothing to evict while scrolling forward --
the cache would grow like `QueuedPagingCache(protectContextWindow = true)` does. The pages next to
the anchor are kept by the rule itself. The strategy may evict pages the context window still
covers; the paginator then narrows the window to the run of cached pages around the page just
loaded, so the snapshot has no hole (see [Protecting the Context Window](#protecting-the-context-window)).
When you scroll one page at a time the window simply loses its far end: with the cache `[2, 3, 4]`
and the window `2..4`, loading page 1 evicts page 4 and leaves the window `1..3`.

A `jump()` to a distant page does not clear the old location the way `ContextWindowPagingCache`
does: the strategy only trims down to `maxSize`, so pages of the previous location are evicted one
by one, farthest first, as later loads complete.

**Composing.** It is a `ChainablePagingCache` and works with `+`. Inner strategies evict before it,
so any other size-limiting strategy in the same chain (`QueuedPagingCache`, `MostRecentPagingCache`)
must have a `maxSize` **greater than or equal to** the `maxSize` of `NearestPagingCache`;
otherwise it picks the victim instead of the rule above. `TimeLimitedPagingCache` combines freely:

```kotlin
val cache = NearestPagingCache<Item>(maxSize = 3) + TimeLimitedPagingCache(ttl = 5.minutes)
```

The cursor counterpart is `CursorNearestPagingCache`, see
[Cursor-Based Pagination → Caching](13.%20cursor-pagination.md#caching).

### Protecting the Context Window

`MostRecentPagingCache`, `QueuedPagingCache` and `TimeLimitedPagingCache` take
`protectContextWindow` (default `true`). It decides what the strategy does with the pages of
`startContextPage..endContextPage` -- the pages the user currently sees.

| `protectContextWindow` | Window pages                         | Consequence                                                                                                                                                                                              |
|------------------------|--------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `true` (default)       | Never evicted                        | `maxSize` can be **exceeded**: when the window is wider than `maxSize` (say `maxSize = 2` and a window of 3 pages) nothing is left to evict and the cache keeps the whole window. The cache never shrinks below the window. For `TimeLimitedPagingCache`, **expired** window pages are kept too, so the window can show data older than `ttl`. |
| `false`                | Evicted like any other page          | `maxSize` (or `ttl`) holds, but the strategy can remove a page the window still covers. The paginator then repairs the window, see below.                                                                |

`MostRecentPagingCache` and `QueuedPagingCache` never evict the page that is being written by that
same write, whatever the flag says (a page that was just written is not expired for
`TimeLimitedPagingCache` either).

**What happens to the window when a window page is evicted.** The paginator keeps one invariant
while it is started: every page of `startContextPage..endContextPage` is cached, so the window has
no holes and both boundaries exist. When an eviction removes a page of the window, the paginator
narrows the window right after the write -- before it publishes the snapshot -- to the longest run
of consecutive cached pages inside the old window that contains the page navigation is working on
(the boundary it is walking past while loading, or the page it has just loaded). The snapshot is
published as usual and has no hole; the pages that fell out of the window stay in the cache as long
as the strategy keeps them.

```kotlin
// FIFO without window protection: the cache holds 3 pages
val paginator = MutablePaginator<Item>(
    core = PagingCore(cache = QueuedPagingCache(maxSize = 3, protectContextWindow = false)),
    load = { page -> LoadResult(api.loadPage(page)) }
)

paginator.jump(BookmarkInt(1))   // window 1..1
paginator.goNextPage()           // window 1..2
paginator.goNextPage()           // window 1..3, cache [1, 2, 3]
paginator.goNextPage()           // loading page 4 evicts page 1 (the oldest)
// window 2..4, cache [2, 3, 4], the snapshot is [2, 3, 4]
```

When the evicted page is in the **middle** of the window, the page navigation has just loaded wins:
with the cache above and the window `2..4`, `goPreviousPage()` loads page 1, whose loading state
evicts page 2 (the oldest). The window shrinks to the run around page 1 -- `1..1` -- and pages
3 and 4 stay in the cache outside the window, so the snapshot is `[1]`. A strategy that evicts by
age cannot know which pages the user is looking at. To keep a bounded window that follows the
scroll in both directions, use [`NearestPagingCache`](#nearestpagingcache), which evicts by
distance, or keep `protectContextWindow = true` and accept that `maxSize` is a soft limit.

The same repair runs wherever the cache is written or the window can be damaged: page loads,
`refresh`, element CRUD and `removeState` on `MutablePaginator`, `core.resize`, `restoreState` and a
transaction rollback. With `ContextWindowPagingCache` alone there is nothing to repair, because it
never evicts a page of the window.

The cursor ports follow the same rules. There the window is the chain of `prev`/`next` links from
`startContextCursor` to `endContextCursor`, and the window narrows to the run of cached pages
around the page navigation is on.

### Restore and Rollback

`restoreState` / `restoreStateFromJson` and the rollback of a [`transaction`](3.%20state.md#transaction-atomic-operations)
rebuild the cache by writing the saved pages through the strategy chain. For eviction strategies
that means:

- **The window comes first.** The capacity and `startContextPage..endContextPage` are restored
  *before* any page is written, so a strategy judges the restored pages by the restored window.
  Pages of the window are not lost, and the `evictionListener` is not called for them when the
  saved pages fit the strategy.
- **Strategy bookkeeping is not restored.** A snapshot or save point holds pages, not the LRU
  recency order, the FIFO queue or the TTL timers. The LRU order and the FIFO queue are rebuilt
  from the order of the writes -- every restored page counts as just inserted, the first written
  page is the first to go -- and the timers of `TimeLimitedPagingCache` start anew, so no restored
  page is expired. For a snapshot made by `saveState` the pages come in ascending order, so with
  `MostRecentPagingCache` and `QueuedPagingCache` the lowest evictable page is the first victim.
- **A saved set that does not fit.** If a snapshot is bigger than the strategy allows, it evicts
  while the pages are written, like for any other write. With `protectContextWindow = true` the
  restored window is protected (so `maxSize` can be exceeded, see
  [Protecting the Context Window](#protecting-the-context-window)); with `false` it may evict
  window pages, and the window then narrows to the run of pages that survived.
  `NearestPagingCache` never evicts while restoring: the pages are written over an empty cache,
  not over a loading state, so the next completed load trims the excess.
- **Cursor caches** write the pages in the order of the chain (from every head along `next`;
  cycles and pages without links last) whatever the order of the snapshot's entries, because
  `CursorContextWindowPagingCache` and the window protection find the pages of the window by
  walking the links that are already written.
- **Subscriptions.** After a restore or a rollback the cache counts as replaced, so
  [`observePages`](15.%20reactive-sources.md#how-a-page-lives) reconciles its subscriptions with
  the restored pages and re-queries every one of them.

### Composing Strategies

Strategies implement `ChainablePagingCache<T>` and can be **chained** with the `+` operator.
The leftmost strategy is the outermost decorator. A write goes through the chain from the outside
in: the outer strategy passes the page to the inner one first, so **inner strategies evict before
outer ones**, and the outer strategy then works on what is left.

```kotlin
// LRU(50) governs eviction count; TTL(5min) evicts stale pages from the inner cache
val cache = MostRecentPagingCache<Item>(maxSize = 50) + TimeLimitedPagingCache(ttl = 5.minutes)

val paginator = MutablePaginator<Item>(
    core = PagingCore(cache = cache),
    load = { page -> LoadResult(api.loadPage(page)) }
)
```

`+` is left-associative, so `a + b + c` builds the chain `a → b → c → InMemoryPagingCache`:

```kotlin
val cache = MostRecentPagingCache<Item>(maxSize = 50) +
            TimeLimitedPagingCache(ttl = 5.minutes) +
            ContextWindowPagingCache(margin = 1)
```

**Size limits must not fight each other.** When two strategies in one chain limit the number of
pages, the one with the smaller `maxSize` reaches its limit first and chooses the victim (with equal
limits the inner one runs first), so the other never applies its own rule. Give every other
size-limiting strategy in a chain with `NearestPagingCache` a `maxSize` at least as large as the
one of `NearestPagingCache`. `TimeLimitedPagingCache` and `ContextWindowPagingCache` combine with
any of them.

An outer strategy is not told when an inner one removes a page. `QueuedPagingCache` handles this
lazily: it skips entries of pages the cache no longer holds and drops them the next time it looks
for a victim, and it compacts its queue when it has grown well past the cache size. A page that an
inner strategy removed and that is written again is a new insertion at the end of the queue, so
`QueuedPagingCache(...) + ContextWindowPagingCache()` keeps first-in-first-out order and its
bookkeeping does not grow with the number of pages that have ever passed through. (Before 10.4.0
the queue kept a stale entry for such a page, so a re-inserted page kept its old priority and the
bookkeeping grew without bound.)

### Eviction Listener

All strategies accept an optional `evictionListener` to react when a page is removed
from the cache (e.g., to persist data before it is lost):

```kotlin
val cache = MostRecentPagingCache<Item>(
    maxSize = 20,
    evictionListener = CacheEvictionListener { evictedPage ->
        println("Evicted page ${evictedPage.page} with ${evictedPage.data.size} items")
    }
)
```

The listener is a `fun interface`, so a lambda works directly.

### Custom Strategies

Implement `PagingCache<T>` to define your own eviction logic. To participate in `+`
composition, also implement `ChainablePagingCache<T>` and use the `withLeaf()` helper
inside `replaceLeaf()`:

```kotlin
class LoggingPagingCache<T>(
    private val cache: PagingCache<T> = InMemoryPagingCache(),
    val tag: String = "PagingCache",
) : PagingCache<T> by cache, ChainablePagingCache<T> {

    override fun replaceLeaf(newLeaf: PagingCache<T>): LoggingPagingCache<T> =
        LoggingPagingCache(cache = cache.withLeaf(newLeaf), tag = tag)

    override fun setState(state: PageState<T>, silently: Boolean) {
        println("[$tag] setState page=${state.page}")
        cache.setState(state, silently)
    }

    override fun removeFromCache(page: Int): PageState<T>? {
        println("[$tag] evict page=$page")
        return cache.removeFromCache(page)
    }

    override fun clear() = cache.clear()
    override fun release(capacity: Int, silently: Boolean) = cache.release(capacity, silently)
}

// Composes with built-in strategies via +:
val cache = MostRecentPagingCache<Item>(maxSize = 50) + LoggingPagingCache(tag = "feed-cache")
```

`cache.withLeaf(newLeaf)` recurses down the delegation chain and replaces the
`InMemoryPagingCache` leaf with `newLeaf`, so your strategy works correctly at any depth.

#### Untracked access — `setStateUntracked` / `peekStateOf`

Not every read or write is a *use* of a page. A live database query
([`observePages`](15.%20reactive-sources.md#per-page-live-queries-observepages)) rewrites a page
whenever its rows change and checks the cached pages on every snapshot, and
[`observe()`](15.%20reactive-sources.md#the-solution-observe--paginatorreactivecache) searches every
cached page for each event's identity — none of that is the user looking at the page. `PagingCache`
therefore has an untracked pair:

| Method                                   | Default            | Meaning                                                            |
|------------------------------------------|--------------------|--------------------------------------------------------------------|
| `setStateUntracked(state, silently)`     | `setState(…)`      | Replace a page **already in the cache** without counting it as use |
| `peekStateOf(page)`                      | `getStateOf(page)` | Read a page without counting it as use                             |

The paginator's own bookkeeping reads use them too: publishing the whole cache to `core.asFlow()`
observers (on every navigation call while `asFlow()` is active) is not a use of every page.

`MostRecentPagingCache` overrides both, so they never move a page in its recency order, and
`TimeLimitedPagingCache` overrides both, so they never restart a TTL timer (also with
`refreshOnAccess = true`). `QueuedPagingCache`, `ContextWindowPagingCache` and `NearestPagingCache` track no usage and
simply forward them down the chain — `by` delegation does that for you. If your own strategy
tracks usage (counts reads, keeps timestamps), override them the same way and forward to
`cache.setStateUntracked` / `cache.peekStateOf`; otherwise there is nothing to do.

The cursor caches have the same pair — `CursorPagingCache.setStateUntracked(cursor, state, silently)`
and `peekStateOf(self)` — overridden the same way by `CursorMostRecentPagingCache` and
`CursorTimeLimitedPagingCache`.

## Persistent Cache (L2)

> **Deprecated since 10.3.0.** The L2 persistent cache (`PersistentPagingCache`,
> `CursorPersistentPagingCache`, `persistentCache`, `flush()`, `affectedPages` / `affectedSelves`,
> `hasPendingFlush`, `warmUpFromPersistent`) is no longer recommended and is no longer supported
> together with the rest of the library: combined with `refresh`, eviction strategies, transactions
> or reactive sources it can cause non-obvious bugs and behaviour. It still works (with a
> deprecation warning) and will be removed in a future major release. Keep your database as the
> single source of truth and bridge it to the paginator with a reactive source instead — see
> [Reactive Sources](15.%20reactive-sources.md).

The paginator supports an optional **second-level persistent cache** that allows pages to survive
process death. While the in-memory `PagingCache` (L1) provides fast synchronous access, a
`PersistentPagingCache` (L2) stores pages in a durable backend (Room, SQLite, files, etc.).

The library ships only the interface -- the implementation is entirely up to you.

### How It Works

**Read path:** L1 (in-memory) → L2 (persistent) → source (network).
When a navigation method encounters a cache miss in L1, it checks L2 before calling the `load`
lambda. If L2 has the page, it is promoted back into L1 and returned immediately -- no loading
indicator, no network call.

**Write path:** After every successful `load` call, the resulting `SuccessPage` (including pages
with empty data) is automatically saved to L2.

### PersistentPagingCache Interface

```kotlin
interface PersistentPagingCache<T> {
    suspend fun save(state: PageState<T>)
    suspend fun saveAll(states: List<PageState<T>>) { states.forEach { save(it) } }
    suspend fun load(page: Int): PageState<T>?
    suspend fun loadAll(): List<PageState<T>>
    suspend fun remove(page: Int)
    suspend fun removeAll(pages: List<Int>) { pages.forEach { remove(it) } }
    suspend fun clear()
    suspend fun <R> transaction(block: suspend PersistentPagingCache<T>.() -> R): R = block()
}
```

All methods are `suspend`, enabling native integration with Room, SQLite, or any async storage.
Override `transaction` to wrap the block in a real DB transaction (e.g., Room's `withTransaction`).
Override `saveAll` / `removeAll` for batch-optimized storage.

### Usage

Provide your implementation when constructing the `PagingCore`:

```kotlin
val paginator = MutablePaginator(
    core = PagingCore(
        cache = MostRecentPagingCache(maxSize = 50),
        persistentCache = RoomPagingCache(dao, json, serializer),
    ),
    load = { page -> LoadResult(api.loadPage(page)) }
)
```

### Example Room Implementation

```kotlin
class RoomPagingCache(
    private val dao: PageDao,
    private val json: Json,
    private val serializer: KSerializer<Article>,
) : PersistentPagingCache<Article> {

    override suspend fun save(state: PageState<Article>) {
        val jsonData = json.encodeToString(ListSerializer(serializer), state.data)
        dao.upsert(PageEntity(page = state.page, data = jsonData, isEmpty = state.isEmptyState()))
    }

    override suspend fun load(page: Int): PageState<Article>? {
        val entity = dao.getPage(page) ?: return null
        val data = json.decodeFromString(ListSerializer(serializer), entity.data)
        return SuccessPage(page, data)
    }

    override suspend fun loadAll(): List<PageState<Article>> =
        dao.getAllPages().map { load(it.page)!! }

    override suspend fun remove(page: Int) = dao.deletePage(page)

    override suspend fun clear() = dao.deleteAll()
}
```

### Persisting CRUD Changes

CRUD operations (`setElement`, `removeElement`, `addAllElements`, `replaceAllElements`,
`removeState`, `+=`) are synchronous and modify only L1. To flush those changes to L2, call
`flush()`:

```kotlin
paginator.setElement("updated", page = 1, index = 0)
paginator.removeElement(page = 2, index = 3)

// Flush all CRUD changes to L2 in one batch
paginator.flush()
```

Inside a `transaction`, CRUD changes are **auto-persisted** on success and **discarded** on
failure — no manual flush needed:

```kotlin
paginator.transaction {
    (this as MutablePaginator).setElement("a", page = 1, index = 0)
    removeElement(page = 2, index = 3)
    // If everything succeeds, changes are auto-persisted to L2.
    // If anything throws, L1 is rolled back and L2 remains unchanged.
}
```

The method tracks affected pages automatically (including cascading effects from rebalancing
and overflow). At flush time, pages still present in L1 as `SuccessPage` are saved; pages that
no longer exist in L1 are removed from L2.

### Inspecting Pending Changes

`MutablePaginator` exposes read-only views of the CRUD tracker so UIs and tests can react to
unsaved state without probing the internals:

```kotlin
if (paginator.hasPendingFlush) {
    showUnsavedIndicator()
}

// Snapshot of page numbers waiting for flush — useful for diagnostics / debug UIs.
val dirty: Set<Int> = paginator.affectedPages
```

| Member            | Type       | Meaning                                                               |
|-------------------|------------|-----------------------------------------------------------------------|
| `affectedPages`   | `Set<Int>` | Snapshot of pages modified by CRUD and not yet flushed to L2          |
| `hasPendingFlush` | `Boolean`  | `true` iff `persistentCache != null` and `affectedPages` is non-empty |

`hasPendingFlush` is always `false` when the paginator has no `persistentCache` — unsaved
changes are meaningless without an L2 backend. Both properties return to their empty/false
state after a successful `flush()` or `transaction { … }`.

On `CursorPaginator`, the equivalent pair is `affectedSelves: Set<Any>` and `hasPendingFlush`,
keyed by `CursorBookmark.self` instead of `page: Int`.

### Warming Up L1 from L2

By default L2 is consulted **lazily** — only when a navigation call misses in L1. For screens
that want the full persisted feed immediately available (e.g. to render a scrollable list on
cold start without a loading state), call `warmUpFromPersistent` once before any navigation:

```kotlin
import com.jamal_aliev.paginator.offset.extension.warmUpFromPersistent

val inserted: Int = paginator.warmUpFromPersistent()
// Every persisted page is now in L1; subsequent jump/goNextPage calls hit L1 directly.
```

Behaviour:

- Reads every entry via `PersistentPagingCache.loadAll()` and inserts each state into L1 silently.
- Pages already present in L1 are **skipped** — the in-memory copy wins on conflict.
- No snapshot is emitted by default. Pass `pageRange = 1..N` (or
  `cursorRange = head to tail` on the cursor variant) if you want a snapshot to fire so the
  warmed-up range becomes visible without a subsequent `jump(...)`.
- Returns the number of pages actually inserted into L1.
- No-op when `persistentCache == null`.

```kotlin
// Cursor-based counterpart — same name, symmetrical signature.
cursorPaginator.warmUpFromPersistent(
    cursorRange = head to tail,
)
```

**Interaction with eviction strategies.** Warming up pushes states through the normal
`cache.setState` entry point, so eviction strategies run on each insert. A
`MostRecentPagingCache(maxSize = 20)` paired with 100 persisted pages will end up with 20 pages in
L1,
not 100. A `ContextWindowPagingCache` with no established context window will effectively
discard every inserted page — prefer `MostRecentPagingCache` for warm-up scenarios, or issue a
`jump(...)` immediately after to establish the context window.

**Concurrency.** `warmUpFromPersistent` does **not** acquire the navigation mutex. Call it on
cold start, before any navigation method fires.

### Lifecycle

- **`restart()`** does **not** clear the persistent cache. Fresh data from the source overwrites
  stale persistent entries via auto-persist.
- **`release()`** does **not** clear the persistent cache. L2 is meant to outlive the paginator
  instance.
- **Transaction rollback** does **not** affect the persistent cache (eventual consistency).
- **MutablePaginator CRUD** operations track affected pages internally. Call
  `flush()` to flush changes to L2 (automatic inside `transaction`).
- Use `hasPendingFlush` / `affectedPages` (or `affectedSelves` on cursor) to inspect tracker
  state; use `warmUpFromPersistent()` to eagerly restore L1 from L2 on cold start.
- To manually clear L2, call `persistentCache.clear()` directly.

### Composing with Eviction Strategies

Persistent cache works alongside eviction strategies. When a page is evicted from L1 (e.g., by
`MostRecentPagingCache`), it remains in L2. The next time that page is requested, it is restored
from
L2 instead of making a network call:

```kotlin
val paginator = MutablePaginator(
    core = PagingCore(
        cache = MostRecentPagingCache(maxSize = 20),     // L1: keep only 20 pages in memory
        persistentCache = RoomPagingCache(dao, json, Article.serializer()),  // L2: unlimited persistent storage
    ),
    load = { page -> LoadResult(api.loadPage(page)) }
)
```
