## goNextPage

Loads the page after the current `endContextPage`. If the paginator hasn't started, it automatically
jumps to page 1.

```kotlin
suspend fun goNextPage(): PageState<T>
```

Behavior:

1. Expands `endContextPage` to find the true end of contiguous success pages
2. Determines the next page number
3. If the next page exceeds `finalPage`, throws `FinalPageExceededException`
4. If the next page is already a `ProgressPage`, returns immediately (deduplication)
5. Otherwise, sets a `ProgressPage`, loads from source, and updates the cache

With a cache that evicts pages of the context window (see
[Protecting the Context Window](6.%20caching.md#protecting-the-context-window)), the window can
shrink while the page loads -- the loading state of the new page can already evict a page of the
window. The window then narrows to the pages that are still cached around the boundary being
walked past, and once the page is loaded it follows that page if the boundary itself was evicted
meanwhile. The snapshot published after each step has no hole. Before step 1 the call repairs a window
that was damaged from outside (a custom strategy, `core.removeFromCache`), so a removed boundary
does not make the call fail.

## goPreviousPage

Loads the page before the current `startContextPage`. Requires the paginator to be started.

```kotlin
suspend fun goPreviousPage(): PageState<T>
```

Behavior mirrors `goNextPage` but in the backward direction. Shows a loading indicator at the top.
Window shrinking works the same way as described for `goNextPage`; `goPreviousPage` no longer
throws when the page at the start of the window was evicted -- the window is narrowed first and the
page before its new start is loaded.

## jump

Jumps directly to any page by bookmark:

```kotlin
suspend fun jump(bookmark: Bookmark): Pair<Bookmark, PageState<T>>
```

If the target page is already cached as a filled success page, returns immediately without
reloading. Otherwise, resets the context window to the target page and loads it. The window is
reset **before** the target's loading state is written, so eviction strategies judge the pages of
the previous location by the new window (for example `ContextWindowPagingCache` drops them).

## jumpForward / jumpBack

Navigate through the bookmark list:

```kotlin
suspend fun jumpForward(): Pair<Bookmark, PageState<T>>?  // null if no more bookmarks
suspend fun jumpBack(): Pair<Bookmark, PageState<T>>?     // null if no more bookmarks
```

When `recyclingBookmark = true`, the iterator wraps around.

## restart

Clears all cached pages, resets the context window to page 1, and reloads it:

```kotlin
suspend fun restart()
```

Ideal for swipe-to-refresh.

If the call is cancelled while page 1 loads, the paginator is put back as it was before the call:
the context window, **all** the pages the call cleared and the dirty marks come back, and a
snapshot is published. The window is restored before the pages are written back, so an eviction
strategy judges them by it. (`CursorPaginator.restart` behaves
differently: it ends with an empty cache and no window, see
[`restart()` semantics](14.%20paginator-vs-cursor.md#1-restart-semantics).)

## refresh

Reloads specific pages in parallel without clearing the cache:

```kotlin
suspend fun refresh(pages: List<Int>)
```

Sets all specified pages to `ProgressPage` (preserving cached data), then reloads them concurrently.
Use the extension `refreshAll()` to refresh every cached page.

The loads run **outside** the navigation lock, so other operations keep working while a refresh is
in flight. When the results arrive, a page is written back only if it still holds the
`ProgressPage` this refresh installed. A page that was changed in the meantime — evicted, cleared by
`restart`/`release`, reloaded by `jump`, relabelled by `removeState`, or overwritten by a reactive
source — keeps its newer state: the stale result is dropped, the page is never resurrected, and its
old dirty flag is dropped too (the newer state is fresher than the mark). Element-level CRUD on the
in-flight page (`setElement` etc.) keeps the page id, so the refresh still owns it and commits over
the edit. The cancellation rollback follows the same rule. With the reactive bridges:

- Events of [`observe()`](15.%20reactive-sources.md) come from the source of truth, so they win over
  the in-flight result and mark the page dirty instead.
- Emissions of a live page ([`observePages`](15.%20reactive-sources.md#how-a-page-lives)) are
  applied to the loading page in place; the refresh still commits its own result (data, metadata
  or error), and the page's query then adopts it or re-queries the page.
